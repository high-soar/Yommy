## システムの全体像

社内の問い合わせを一覧・検索し、詳細を確認して担当者やステータスを更新し、コメントを追加するシステムを題材にします。このリポジトリでは React、TypeScript、Next.js による画面開発を学び、実バックエンドは作成しません。画面からの API 通信は OpenAPI 契約に沿った mock で再現し、開発・UT・IT では MSW の利用、リリース相当・PT では別コンテナ Mock API サーバーの利用を想定します。

対象範囲は次のとおりです。

- ステータス・担当者・プロジェクトによる問い合わせ一覧の絞り込み
- 問い合わせ詳細とコメントの表示
- 担当者・ステータスの更新とコメント追加
- ログイン認証・ロール別アクセス制御（一般ユーザー・管理者ユーザー）
- ロール別ダッシュボード表示・問い合わせ新規起票・ユーザー/プロジェクト管理
- 開閉式サイドバーによるナビゲーションと画面離脱防止（Dirty State ガード）
- 読み込み中・データなし・API エラー・権限エラー（403/404）の表示

API 契約は `docs/ed/api/openapi.yaml` を正本として定義します。具体的なパスやデータ形式は OpenAPI 設計で確定し、開発・単体テスト・結合テストではその契約に対応する MSW mock を使います。リリース相当の接続確認や総合テスト（PT）では、同じ API 契約とモックデータを活用する Mock API を別コンテナで提供し、画面から `/api` 経路で接続します。実バックエンドの開発はこの学習範囲に含めません。

## 開発工程

工程は次の順に進めます。各工程の成果物をレビューし、完了を確認してから次の工程に進みます。

| 工程     | 主な成果物・完了条件                                                                                                                                                                                                          |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RD       | システムの背景・目的、対象利用者、スコープ（含む/含まない機能）、システム受け入れ条件を合意する（[Step 1](rd/step1.md)、[Step 2](rd/step2.md)、[Step 3](rd/step3.md)）                                                        |
| ED       | 業務要件、画面一覧・遷移・画面仕様、REST API 契約、受け入れ条件を合意する                                                                                                                                                     |
| ID       | React の構成、状態・データの流れ、API 通信、入力検証、エラー処理、テスト設計を確定する                                                                                                                                        |
| C・UT    | 承認済み ID に沿って実装し、単体テストを通す                                                                                                                                                                                  |
| IT       | OpenAPI 契約に沿った mock API を使い、前Stepまでの開発範囲を当Step仕様に合わせて包含・進化させ、今Step新機能と統合したシステム全体のシナリオにより、画面・API・状態をまたぐ一貫動作（全体結合・リグレッション保証）を確認する |
| PT       | 業務で定義された PT の計画・判定基準に沿って全体を確認する                                                                                                                                                                    |
| PT後改善 | VRT導入、Storybook・Vitest連携によるUIテスト基盤の改善                                                                                                                                                                        |

AI は各工程の調査、草案、実装、テスト作成を補助します。生成物の要件適合性と工程完了の判断は人が確認します。

## 共通記載形式

各 RD/ED/ID/IT/PT/PT後改善 設計書および本 `docs/README.md` に、状態・更新日・関連項目を記載します。Markdown形式の設計書では冒頭に次の表を置きます。OpenAPI YAMLでは仕様拡張フィールド `x-design-metadata` に同じ情報を記録します。

| 項目                | 内容                                                                                                                                                                |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 状態                | `Draft (Step 3)`                                                                                                                                                    |
| 更新日              | `YYYY-MM-DD`                                                                                                                                                        |
| 関連する ED/ID 項目 | `docs/rd/...#見出し`、`docs/ed/...#見出し`、`docs/id/...#見出し`、`docs/it/...#見出し`、`docs/pt/...#見出し`、または `docs/vrt/...#見出し`。該当なしの場合は `なし` |

OpenAPI YAMLでリポジトリルートの `x-design-metadata` に記載する例です。

```yaml
x-design-metadata:
  status: "Draft (Step 3)"
  updated: "YYYY-MM-DD"
  related:
    - docs/ed/...#見出し
```

- 状態は **`Draft (Step N)`**、**`Review (Step N)`**、**`Approved (Step N)`** のように対象 Step を付与して管理します。
  - `Draft (Step N)` は当該 Step における作成中、`Review (Step N)` はレビュー依頼中・工程内レビュー待ち、`Approved (Step N)` は人による工程承認完了を表します。
  - **Step 間のドキュメントライフサイクル**:
    - 前 Step で承認された成果物は、新 Step 開始時点では **`Approved (Step N-1)`** のまま維持します（一括で Draft 等に戻す必要はありません）。これにより、「前 Step 承認済みのベースラインであること」と「現 Step で未改修・着手前であること」を同時に識別できます。
    - 現 Step の改修対象となった成果物は、作業・PR 提出時に **`Review (Step N)`** とし、個別 PR がマージされても `Review (Step N)` を維持します。
    - 現 Step の工程承認 Issue において人間レビュアーが工程全体を承認した段階で、対象工程の全成果物を一括で **`Approved (Step N)`** に更新します。AI は自ら `Approved (Step N)` に変更しません。
    - 現 Step で変更不要（仕様維持）の成果物は、工程承認時に「現 Step 適用確認」を行い `Approved (Step N)` に追認昇格するか、あるいは `Approved (Step N-1)` のまま維持することを工程計画書で定めます。
- 更新日は内容を最後に更新した日付を ISO 形式（`YYYY-MM-DD`）で記載します。
- 関連項目はリポジトリルートからのパスと見出しアンカー（`path/to/file.md#見出し`）で参照し、複数ある場合はすべて記載します。該当なしの場合、Markdownでは `なし`、YAMLでは `related: []` とします。見出しアンカーは参照先ファイルの実際の見出し文字列（GitHub Flavored Markdown のスペース→ハイフン変換・記号除去規則）と完全に一致させ、リンク切れを防止します。

## 設計書のレビューと AI 利用

- ED が `Approved` になってから ID、ID が `Approved` になってから C・UT に進みます。
- AI には対象工程、参照する承認済み資料、今回の作業範囲を明示します。
- AI の提案は要件・API 契約と照合し、差分と検証結果を人がレビューしてから採用します。
- 設計書・API 契約の作成および PR レビューでは、変更差分（diff）だけでなく対象ファイル全体と関連正本を照合し、以下の整合性を確認します。
  1. **ファイル全体と旧記述の点検**: 既存設計書の改修時に、未変更行に残存する過去 Step の古い記述（解決済み課題メモ、旧パス、旧仕様）が新しい仕様と矛盾していないこと。
  2. **OpenAPI 契約との 1 対 1 整合**: 画面仕様書・内部設計書と `docs/ed/api/openapi.yaml` の間で、フィールド識別子（例: `name` 等）、クエリパラメータ名、必須属性（`required`）、文字数・正規表現制約（`minLength`, `maxLength`, `pattern`）、HTTP ステータスコードが完全に一致していること。
  3. **双方向トレーサビリティ**: 受け入れ条件（`SYS-AC-*`, `AC-*`）、画面遷移（`TR-*`）、ガード条件などを追加・変更した際、上位・同階層の設計書（システム概要のトレーサビリティマトリクス、画面一覧、画面遷移表等）との間で双方向の対応関係が漏れなく同期されていること。
  4. **検証可能性と解決ゲートの明確化**: 条件の定義がない曖昧な併記（「A または B」等）を排除し、非機能・接続要件の観測可能な判定基準と、後続工程への申し送り事項の解決先（対象工程・成果物・ブロッカー有無）を明記すること。
- PR レビューおよび工程完了レビューにおける指摘・コメントの記述形式は、[レビューコメント記述仕様（SSOT）](review-comment-format.md) に従います。
- **後工程・別工程での前工程成果物に対する不整合・バグ是正フロー（手戻り変更管理）**:
  後続の設計工程（例: ID作成中にED不整合が発覚）やテスト工程（C・UT, IT, PT）において、承認済みの前工程成果物（RD/ED/ID/OpenAPI）の不備・矛盾が発覚した場合、以下のフローで規律ある是正を行います。
  1. **不備のトリアージと Issue 切り出し**:
     - **軽微な不備（`[P3]` / タイポ、誤字、軽微な注釈など）**: 独立 Issue は不要とし、作業中の現行 PR 内で併せて修正可能（コミットメッセージに `docs(<phase>): ...` を記載）。
     - **仕様・設計の矛盾・欠陥（`[P0]`〜`[P2]` / 業務仕様、画面遷移、権限、API契約、受け入れ条件の変更を伴うもの）**: 必ず独立した手戻り是正 Issue（例: `[Fix/ED] ...`、Issue #220 等）を起票する。
  2. **承認済み成果物の再承認ルール（局所的再承認）**:
     - 承認済みドキュメントを修正する場合、PR 提出時は `状態: Review (Step N)` とする。
     - 人間レビュアーが PR をレビュー・マージした時点で、当該ドキュメントは即座に **`Approved (Step N)`** に復帰したものとみなす（工程全体の工程承認 Issue をリオープン・全件再レビューする必要はない）。
  3. **影響波及分析（Impact Analysis）と申し送り義務化**:
     - 是正 Issue の完了条件には、上位設計書・同一工程の関連設計書・後続設計書・既存コード/テストへの影響波及確認（Impact Checklist）を含め、影響を受ける後続作業 Issue へコメントで申し送りを完了すること。
  4. **テスト工程（C・UT, IT, PT）での設計書同期原則**:
     - テスト工程で不備が検出され、原因分類が `D`（設計・仕様不備）である場合、ソースコードやテストコードのみを修正して設計書を放置することを禁止する。
     - 不備記録シート（`evidence/*-bug-record.md`）の是正内容欄に、コード修正コミットだけでなく設計書（ED/ID等）の修正コミット・PR を必ずセットで記録する。
