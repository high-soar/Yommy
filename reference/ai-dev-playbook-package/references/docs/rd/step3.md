この文書は Step 3 における「Next.js への移行・コンテナ提供方針」および「UT / IT / PT の責務切り分けとテスト規約の刷新方針」を定義する要件定義書です。Step 3 の ED・ID・各工程スキルは本書に基づいて詳細化・更新します。

## 1. 背景・目的

Step 2 の次の取り組みとして、以下の 2 点を主軸にシステム基盤と品質保証体系を進化させます。

1. **Next.js への移行とコンテナ提供の技術検証**:
   - 既存画面・機能の振る舞いを維持し、画面ソース（`src/features/`、`src/shared/`）の大幅な変更を避けつつ、Vite + 自前ルーター構成から **Next.js (App Router)** へ移行し、コンテナイメージによる画面提供と別コンテナ Mock API との接続を検証します。
2. **UT / IT / PT の切り分けとテスト規約の整備**:
   - **UT**: テストの集約・省略による効率化よりも、**「テストケース作成ルールの単純化」** と **「ソースコードとテストの 1 対 1 比較により、人間が網羅性（十分性）を簡易・確実にチェックできること」** を第一目的とした項目上げルールへ刷新します。
   - **IT**: 実ブラウザ（Playwright）駆動へ移行し、画面単位のふるまい・画面遷移・異常系など UT でカバーしきれない結合挙動を検証するとともに、**トレース（`trace: "on"`）を常時記録**して視覚・通信の両面から監査可能な証跡を残します。
   - **PT**: 現状通り、本番相当環境での業務受入シナリオ確認および非機能品質検証（Lighthouse / バンドルサイズ / アクセシビリティ / レスポンシブ）を実施します。

## 2. Next.js 移行およびコンテナ提供方針

### 2.1 ルーティングとコンポーネント移行方針

- **App Router によるファイルベースルーティングへの移行**:
  - 現行の自前ルーター（`src/app/AppRouter.tsx`、`src/app/routes.ts`）を廃止し、Next.js の App Router（`src/app/**/page.tsx`、`layout.tsx`、`not-found.tsx`）へ移行します。
  - ルート構成例:
    - `/login` → `src/app/login/page.tsx`
    - `/dashboard` → `src/app/(authenticated)/dashboard/page.tsx`
    - `/tickets` → `src/app/(authenticated)/tickets/page.tsx`
    - `/tickets/new` → `src/app/(authenticated)/tickets/new/page.tsx`
    - `/tickets/[id]` → `src/app/(authenticated)/tickets/[id]/page.tsx`
    - `/admin/management` → `src/app/(authenticated)/admin/management/page.tsx`
    - 未定義パス → `src/app/not-found.tsx`
- **SSR は主目的とせず、Client Components 中心で構成**:
  - 既存の画面・UI コンポーネント（`src/features/`、`src/shared/`）およびカスタムフックは `"use client"` を基本とし、既存の React 状態管理や MSW との親和性を維持します。
  - 画面遷移・URL 参照 API のみ `window.history` 直接操作から `next/navigation`（`useRouter`, `usePathname`, `useSearchParams`）へ置き換えます。
- **グローバル CSS の一元管理**:
  - Next.js の Root Layout（`src/app/layout.tsx`）と Storybook（`.storybook/preview.ts`）で読み込むグローバル CSS を同一ファイルに統一し、Storybook VRT と実アプリの描画スタイルの一致を保証します。

### 2.2 API モックとコンテナ提供構成

- **開発・UT・IT**:
  - 引き続き `docs/ed/api/openapi.yaml` を唯一の正本（SSOT）とし、`src/mocks/` の MSW モックを利用します。
- **リリース相当の接続確認（PT・コンテナ検証）**:
  - 画面を Next.js コンテナイメージとして提供します。
  - OpenAPI 契約と既存のモックデータ（`src/mocks/db/`）を活用する **Mock API サーバーを別コンテナ**で提供し、画面から API へ本番想定の経路（`/api` 経路の Rewrites またはリバースプロキシ等）で接続します。
  - 実バックエンドの開発は対象外とし、MSW 自体をコンテナ化するのではなく、契約とモックデータを活用する軽量 API サーバーを別途用意します。

### 2.3 対象外とする機能（将来課題として維持）

Step 2 から引き継いだ以下の機能・要求は、Step 3 でも引き続き対象外とし、将来の実バックエンド開発や運用拡張時に検討します。

- **管理者操作（プロジェクト削除、ロール変更）の監査ログ永続化**: Step 2 PT 申し送り事項（No.3）。Step 3 では実バックエンド・永続化層の開発を行わないため、引き続き対象外とします。
- **チケットの物理削除・コメントの編集および削除**: 業務データ保全およびスコープ管理のため対象外を維持します。
- **多要素認証（MFA）およびブルートフォース攻撃対策**: 認証セキュリティの高度化は将来課題として維持します。
- **ダッシュボードの未完了判定しきい値カスタマイズ**: 固定しきい値仕様を維持します。

### 3.2 UT（単体テスト）の項目上げ・作成ルール

#### (1) ファイル種別ごとの作成ルール（例外なしの1対1対応）

テスト方針の単純化を最優先し、薄いラッパー（`src/app/**/page.tsx` 等）を含め、**すべてのファイルに対して例外なく一律のルールを適用**します。

| 対象ソースファイル                                | 必須作成ファイル                | 補完ファイル                                       | 作成・網羅ルール                                                                                                                                                                                                                                                                                                                                      |
| :------------------------------------------------ | :------------------------------ | :------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`*.tsx`**<br>（全コンポーネント・Page・Layout） | **`*.stories.tsx`**<br>（必須） | **`*.test.tsx`**<br>（Story 実行 ＋ ロジック補完） | 1. 対象コンポーネントの Props 分岐・表示バリエーション・基本操作（`play` 関数）を **漏れなく `.stories.tsx` に Story として上げる**。<br>2. `.test.tsx` では `composeStories` を用いて全 Story の描画・`play` 関数を実行する。<br>3. **Story だけではカバーしきれない内部ロジック分岐**がある場合は、`.test.tsx` 内の Vitest テストケースで補完する。 |
| **`*.ts`**<br>（Hooks / API / 関数 / Store 等）   | **`*.test.ts`**<br>（必須）     | —                                                  | 関数の入出力、カスタムフックの状態遷移、非同期制御、エラー分岐を `.test.ts`（フック等で DOM/Provider が必要な場合は `.test.tsx`）で漏れなく網羅する。                                                                                                                                                                                                 |

#### (2) Story でカバーしきれないロジックを `.test.tsx` で補完する基準

- **`.stories.tsx` で上げるもの**:
  - 視覚的に意味のある状態バリエーション（初期状態、選択状態、Loading、Empty、Error、Disabled、ロール別表示など）および代表的なユーザー操作（クリック・入力の `play` 関数）。
- **`.test.tsx` の Vitest コードで補完するもの**:
  - Story として個別に切り出すとカタログが冗長になる細かなイベント分岐（例: `AdminManagementTabs.tsx` のキーボード操作 `ArrowRight` / `ArrowLeft` / `Home` / `End` / 無関係キー押下時の `default` 早期リターン等）。
  - Unmount 時のクリーンアップ処理、AbortSignal による中断、複雑なコールバック引数の組み合わせ検証など。

#### (3) 親子コンポーネント間の独立性ルール（効率化のための省略禁止）

- **対象コンポーネント内のバリエーションのみを考える**:
  - 「親コンポーネントのストーリー・テストで子コンポーネントのバリエーションも考慮し、親の試験のみで済ませる」といった効率化は行いません。
- **親コンポーネントの UT 範囲**:
  - 親コンポーネント（`Page` 等）の Story / UT では、**親自身が持つ状態分岐・レイアウト責務・子への Props 受け渡し**のみを検証します。
  - 子コンポーネント固有の入力境界や細かな表示バリエーションは、必ず**子コンポーネント自身の `.stories.tsx` / `.test.tsx`** で検証します。
- **狙い**:
  - 人間がレビューする際、**「対象の `.tsx` ソースコード」と「同階層の `.stories.tsx`（＋`.test.tsx`）」の 2 つを並べるだけで、分岐（`if` / `switch` / 三項演算子）に対するテストの十分性を即座に確認できる**ようにします。

#### (4) カバレッジ計測と VRT

- **Vitest カバレッジ（C0 / C1 網羅）**:
  - カバレッジ計測を継続し、**C0（命令/行）および C1（分岐）の 100% 網羅**を原則とします（型定義ファイル等の非実行コードを除く）。
- **Storybook VRT の継続と一本化**:
  - 全 `.tsx`（部品から Page / Layout まで）の表示バリエーションが `.stories.tsx` に揃うため、VRT（`npm run test:vrt`）は **UT の Storybook 対象に一本化**して視覚的デグレを担保します。

### 3.3 IT（結合テスト）の実施・トレース記録ルール

#### (1) IT のテスト対象範囲

UT で各コンポーネント単体の C0/C1 が網羅されている前提のもと、IT では **Playwright Test（実ブラウザ）** を用いて以下を検証します。

1. **画面単位でのふるまい網羅**:
   - 各画面において、初期表示 → 検索・絞り込み・ソート・ページング → フォーム入力・API 送信 → 画面への即時反映が、実ブラウザとモック API を通じて一貫して動作すること。
2. **画面遷移・URL クエリ同期・履歴制御**:
   - Next.js App Router による画面間遷移、未認証リダイレクトとログイン後の元画面復帰、ブラウザバック/フォワードによるクエリ復元、Dirty State ガード（離脱防止モーダル）の動作。
3. **異常系・境界系の画面挙動**:
   - API 401（トークン失効時の自動ログアウト・リダイレクト）、403（ロール権限エラー）、404（未存在データ・未定義パス）、500（エラー表示と再試行復帰）など、UT 単体ではカバーしきれない画面全体の異常系挙動。

> **※ IT での VRT は実施しない**:
> 画面・部品の視覚的回帰テストは UT（Storybook VRT）で 100% カバーされるため、スナップショット二重管理や動的データ起因のフレイキー化を避けるべく、IT では `toHaveScreenshot` による VRT は行いません。

#### (2) トレース常時記録（`trace: "on"`）とエビデンス構成

IT 用 Playwright 設定では以下を標準とします。

- **Playwright 設定**:
  - `use: { trace: "on" }`: 全テストケース（成功時含む）でトレースを常時記録。
  - `reporter: [["html", { open: "never" }], ["json", { outputFile: "playwright-report/it-results.json" }], ["list"]]`: HTML レポートと構造化 JSON データを常時出力。
  - テストコード内では `test.step("日本語の操作ステップ名", ...)` を用いて手順を構造化し、レポート上でテスト仕様書と同等の可読性を確保。
- **取得するエビデンスと確認可能な内容**:
  1. **Playwright Trace (`trace.zip`) & HTML レポート**:
     - 操作ステップごとの前後 DOM スナップショット、画面表示、アドレスバー URL 遷移、Network 通信（API リクエスト/レスポンス JSON・HTTP ステータス）、Console エラー/Warning の有無を Trace Viewer 上で 1 ステップずつ追跡・確認可能にする。
  2. **JSON レポートからの Markdown 結果サマリー表**:
     - 実行結果 JSON（`playwright-report/it-results.json`）から全シナリオ・テストケースの合否・実行時間を集計した Markdown レポートを生成。
- **エビデンスの保管場所（2層管理）**:
  - **Git リポジトリにコミットするもの（`docs/it/evidence/`）**:
    - JSON レポートから生成した **IT 実行結果サマリー表（Markdown）**（`docs/it/evidence/it-test-result.md`）
    - **結合テストバグ記録シート**（`docs/it/evidence/it-bug-record.md`）
  - **ローカル出力 ＆ CI Artifact で保持するもの**:
    - **`playwright-report/` 一式（HTML レポート ＋ 全ケースの `trace.zip` ＋ `it-results.json`）**。ローカルでは `npx playwright show-report` で即時確認し、GitHub Actions では Artifact として保存して PR レビュー・工程承認時に監査可能とする。

### 3.4 PT（総合テスト・受入テスト）の方針

- **現状通り継続**:
  1. **本番相当環境（Next.js コンテナ ＋ Mock API コンテナ）での業務受入シナリオ確認**:
     - システム受け入れ条件（`SYS-AC-*`）に基づく実ブラウザ手動受入テストとエビデンス記録（`docs/pt/evidence/acceptance-test-result.md`）。
  2. **非機能・品質特性検証**:
     - Lighthouse 監査（Performance / Accessibility / Best Practices）
     - **本番クリーンビルドのバンドルサイズ計測（初期ロード 100.0 kB 未満の達成）**:
       - Step 2 PT での申し送り事項（No.1）に基づき、Next.js App Router による自動コード分割（Route-based Code Splitting）を活用し、初期ロード JavaScript バンドルサイズを 100.0 kB 未満に抑制する（モック除外 DCE の確認含む）。
     - キーボード操作性、WCAG 2.1 AA コントラスト比、レスポンシブ表示確認（1280px / 375px）
  3. **品質分析・評価レポート**:
     - UT → IT → PT を通じた欠陥記録と総合欠陥除去率（Total-DRE）の算定（`docs/pt/quality/step3.md`）。
