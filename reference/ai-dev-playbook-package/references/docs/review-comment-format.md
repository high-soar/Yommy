# レビューコメント記述仕様（SSOT）

このドキュメントは、本リポジトリにおける Pull Request（PR）レビューおよび工程完了レビュー（Issue コメント）で人間レビュアーおよび AI エージェントが使用するコメントフォーマットの正本（Single Source of Truth: SSOT）です。

---

## 1. 基本原則

1. **事実と証拠に基づく記述**:
   - 変更差分、承認済み要件（RD）、設計書（ED/ID）、テストコード、または実行証跡に裏付けられた具体的な指摘のみを報告します。
   - 個人のコードスタイルの好みや推測に基づくリスクを欠陥（Defect）として報告しないでください。
2. **重要度（Severity）の明記**:
   - 各指摘には `[P0]` 〜 `[P3]` の重要度を付与し、重要度の高い順に並べます。
3. **再現・修正に必要な 4 要素の網羅**:
   - すべての指摘は「対象（Location）」「問題（Problem）」「根拠・影響（Impact）」「改善案・引き継ぎ（Recommendation）」を含めます。

---

## 2. 重要度（Severity）の定義

| 重要度     | 名称                 | 定義・判定基準                                                                                                      |
| :--------- | :------------------- | :------------------------------------------------------------------------------------------------------------------ |
| **`[P0]`** | 致命的（Critical）   | システムの停止、データの破壊・喪失、重大なセキュリティ脆弱性、CI/環境の完全破損など、即座に対処が必要な致命的欠陥。 |
| **`[P1]`** | 重大（High）         | 承認済み要件や API 契約の未達、機能不全、後続工程の着手を妨げるブロッカー、仕様の重大な不整合。                     |
| **`[P2]`** | 通常・改善（Medium） | 要件を満たしているが設計整合性・保守性・型安全性を損なう問題、境界値・異常系の考慮漏れ、軽微なドキュメント不整合。  |
| **`[P3]`** | 軽微（Low）          | 将来の改善提案、軽微な記述揺れ、可読性向上など、即座に修正しなくても後続作業に影響を与えない事項。                  |

---

## 3. 単一指摘（Finding）の共通形式

PR のインラインレビューコメント、PR レベルの単一指摘、および Issue での個別指摘には次の形式を使用します。

```markdown
### [重要度] 簡潔で具体的な要約

- **Location**: `path/to/file.ext:行番号`
- **Problem**: 不正な振る舞い・不整合な記述内容と発生条件。
- **Impact**: 承認済み要件・仕様・設計正本との齟齬、システムや利用者への影響。なぜこれが誤りなのかの根拠。
- **Recommendation**: 具体的な修正案や後続 Issue 解決フローへの申し送り。
```

> **Note**: 本リポジトリでは日本語での記述を標準とします。英語で報告する場合も同じキー（`Location`, `Problem`, `Impact`, `Recommendation`）を使用します。

---

## 4. PR レビューコメントの運用形式

### A. インラインレビューコメント

- 該当する差分行に直接アンカーして上記の「単一指摘（Finding）形式」で投稿します。

### B. PR 全体レビューコメント（PR レベル）

- 差分行に紐付けられない指摘がある場合、または指摘事項がない場合に PR 本文へのコメントとして投稿します。
- **指摘なしの場合**:
  ```markdown
  ## レビュー結果

  - 確認範囲: ...
  - 実行した検証: `npm run lint`, `npm test` 等
  - 判定: Actionable な指摘事項はありません。
  ```

### C. レビューコメントスレッドの返信と収束

- 実装者は各指摘スレッドに対し、修正コミット（SHA）や検証結果、または対応しない理由を返信します。
- レビュアーは修正を確認できたスレッドのみを解決（Resolve conversation）します。未検証のままスレッドを閉じません。

## 5. 工程完了レビュー・多数指摘時の集約コメント形式

複数成果物を横断検証する工程完了レビュー（Issue コメント）や、指摘が多数（10 件以上など）に及ぶ場合は、人間レビュアーや後続作業者の認知負荷を下げ迅速にトリアージできるよう、**サマリー表** と **重要度別セクション** を使って構造化します。

### 指摘 ID（Finding ID）の採番ルール（レビュー回次プレフィックス方式）

工程完了レビューは、指摘事項の是正対応や確認範囲の追補によって同一 Issue 内で複数回（第1回、第2回…）実施されることがあります。指摘 ID の衝突や混同を防止し、対応報告や PR、コミットとのトレーサビリティを担保するため、以下の採番規則を適用します。

1. **ID 形式**: `R<ラウンド番号>-<2桁連番>`（例: `R1-01`, `R1-02`, `R2-01` 等）
   - `<ラウンド番号>`: 当該 Issue におけるレビューの回次番号（初回レビューは `1`、2回目レビュー/再レビューは `2`、以降連番）。
   - `<2桁連番>`: そのレビュー回次の中で `01` から開始する2桁のゼロ埋め連番。
2. **初回レビュー（Round 1）**:
   - `R1-01`, `R1-02`, `R1-03`... と採番します。
3. **2回目以降のレビュー（再レビュー・追補レビュー: Round 2〜）**:
   - **新規指摘事項**: 当該回次のプレフィックスを用いて `R2-01`, `R2-02`... と新たに採番します。
   - **前回までの未解消指摘の再掲・残存確認**: 前回の指摘が未解消であることを報告・追跡する場合は、新しい ID を付番せず、**初出時の ID（例: `R1-01`）を維持**してサマリー表に記載します（「現状: 未解消」等のステータスを付記）。
4. **効果・目的**:
   - 是正対応報告コメント、PR、コミットメッセージ等で「どのレビュー回次のどの指摘か」が一意に特定でき、ID の衝突や誤認を完全に防止します。

```markdown
## 工程完了レビュー結果

- **工程**: （例: Step 2 外部設計 (ED)）
- **対象成果物**: （例: docs/ed/ 配下の外部設計成果物一式）
- **対象 SHA**: `commit-sha`
- **確認した完了条件・ゲート**: （例: 先行作業 Issue #98〜#105 の完了、docs/rd/step2.md との整合）
- **実行したチェック**: （例: 独立 subagent による 3 観点検証、Prettier 検証）
- **未確認事項**: （例: 人間レビュアーによる承認は未実施）

### 指摘一覧サマリー

| ID    | 重要度 | 対象成果物 / ファイル                | 要約                                         |
| :---- | :----- | :----------------------------------- | :------------------------------------------- |
| R1-01 | P1     | `docs/ed/api/openapi.yaml:25`        | 認証・セッション方式が API 契約で未定義      |
| R1-02 | P1     | `docs/ed/api/openapi.yaml:748`       | コメント投稿リクエストで投稿者を任意指定可能 |
| R1-03 | P2     | `docs/ed/screens/ticket-create.md:5` | 工程完了レビュー前に先行して Approved と記載 |

---

### 指摘 (P1: 重大・後続工程ブロッカー)

#### [P1] R1-01: 認証・セッション方式が API 契約で未定義

- **Location**: `docs/ed/api/openapi.yaml:25`
- **Problem**: 全体で `security: []` と定義されており、モック認証ガードを実装するための方式が示されていない。
- **Impact**: 保護対象 API にセッション情報をどう渡すかが契約から判別できず、ID 工程で実装できない。
- **Recommendation**: Cookie または Bearer 等の認証方式を定義し、保護 API に要件を明示する。

...

### 指摘 (P2: 設計不整合・品質改善)

#### [P2] R1-03: 工程完了レビュー前に先行して Approved と記載

- **Location**: `docs/ed/screens/ticket-create.md:5`
- **Problem**: 工程承認 Issue が未クローズの段階で、個別作業完了時に先行して `Approved` に更新されている。
- **Impact**: ガバナンス上の承認状態が不揃いになり、AI が Approved を変更できないルールと矛盾する。
- **Recommendation**: 個別作業時は `Review` にとどめ、工程承認時に人間承認に基づき一括更新する。
```

> **Note**: 指摘が少ない場合（数件程度）は、サマリー表を省略して重要度順の箇条書きとしても構いませんが、4 要素（Location, Problem, Impact, Recommendation）の構造および指摘 ID（`R1-01` 等）の規則は必ず維持してください。
