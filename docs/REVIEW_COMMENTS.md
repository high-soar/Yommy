# 要件定義書レビューコメント

`docs/REQUIREMENTS.md` を確認しました。以下の点について確認・提案があります。

## 1. データ構造・オフライン対応について (4. データ構造)
* **Episodesテーブルの扱い:**
    * 要件書では「※ オフライン対応や高速化のために必要に応じて実装」とありますが、Fire HD（タブレット）での利用シーンを考えると、オフラインでの閲覧や、目次表示の高速化（毎回スクレイピングしない）は重要と考えられます。
    * **提案:** `Episodes` テーブルを **必須** とし、目次情報をローカルにキャッシュする設計を推奨します。これにより、「次へ」ボタンでの遷移もスムーズになります。

## 2. 更新チェックのロジック (3.A.2, 5.UC2)
* **判定基準:** 現在は「`取得した総話数` > `DBの総話数`」で更新判定を行うとなっています。
* **懸念点:** 作者が改稿などで話を削除・統合した場合、総話数が減る可能性があります。単純な大小比較では更新を見落とす（あるいは誤作動する）可能性がありますが、個人利用の範囲であれば許容範囲でしょうか？
    * **提案:** より厳密に行うなら「最新話のタイトル」や「更新日時」も併用しますが、実装コストとのトレードオフで現状のままでも可とします。

## 4. エラーハンドリング
* **スクレイピング失敗時:**
    * サイト側の仕様変更や通信エラーで取得できない場合の挙動が未定義です。
    * **提案:** トースト表示や「リトライ」ボタンの設置を基本動作として組み込みます。

## 5. ターゲットサイト (1. プロジェクト概要)
* **カクヨム（優先）:**
    * サイト構造の変化に弱いため、解析ロジックは別クラス（Repository/DataSource）に切り出して保守しやすくする設計にします。
