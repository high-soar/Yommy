## 運用ルールと分類凡例

### 記録必須6項目

| 項目名                   | 説明                                                                                                                                                      |
| :----------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **No.**                  | 当該タスク内での連番（1, 2, ...）                                                                                                                         |
| **検出手段**             | 不備が最初に確認された手段（例: `TDD Red（既存不備の検出）`, `Green`, `Refactor`, `自動検証（Vitest/VRT）`, `AIレビュー` 等）                             |
| **成果物区分**           | `製品コード` または `テスト・モック等支援成果物`                                                                                                          |
| **対象箇所**             | 不備が存在したファイル名・関数名・モジュール名                                                                                                            |
| **原因分類**             | 原因分類コード（L / S / D / B / A）                                                                                                                       |
| **不備の概要と是正内容** | 不備の具体的な現象・根本原因、およびどのように是正したか（コミットリンク・PRリンクを含む）。**原因分類 `D` の場合は設計書同期コミット/PR を必ず併記**する |

### 原因分類コード（5分類）

- **L (Logic)**: ロジック誤り（条件分岐ミス、ループ誤り、真偽値反転、計算式の誤り）
- **S (State)**: 状態遷移誤り（React state 更新漏れ、Context 値の不整合、ライフサイクル・初期化順序）
- **D (Design)**: 設計・仕様誤認（OpenAPI 契約や ED/ID 設計書の見落とし、型不一致、パス・パラメータ誤認）
- **B (Boundary)**: 境界値未考慮（`null` / `undefined` の考慮漏れ、空文字・空配列、文字数上限・サロゲートペア）
- **A (Async)**: 非同期制御不備（Promise ハンドリング漏れ、`AbortController` 未連携、Race Condition、遅延レスポンス上書き）

### 成果物区分の定義

- **製品コード**:
  `src/` 配下のプロダクションコード（画面、フック、コンポーネント、レイアウト、API クライアント等）に存在した不備。
  C・UT 工程の品質を測る「製品コードの KLoC あたりバグ密度」および「テストケースあたりバグ密度」の算定対象（分子）となります。
- **テスト・モック等支援成果物**:
  単体テストコード、MSW ハンドラー・データストア、Storybook、設定ファイル、別コンテナ Mock サーバー設定等の不備。
  製品コードのバグ密度を歪めないよう別集計とし、製品コード欠陥数には含めません。

### 原因分類 `D`（設計・仕様不備）検出時における設計同期ルール

> [!IMPORTANT] コードのみ修正の禁止と設計書即時同期義務
> [AGENTS.md](../../../AGENTS.md) §4、[docs/id/test-design.md](../../../docs/id/test-design.md) §9.1、および [.github/skills/c-ut-workflow/SKILL.md](../../../.github/skills/c-ut-workflow/SKILL.md) §10.2 に基づき、原因分類 `D`（設計・仕様不備、OpenAPI/ID 契約不一致）が検出された場合は、**コードのみを修正することは厳格に禁止**されています。
>
> 1. 必ず対応する設計書（`docs/ed/`, `docs/id/`, `docs/ed/api/openapi.yaml`）を即座に是正する。
> 2. 本シートの「不備の概要と是正内容」欄に、**コード修正コミット/PR と設計書修正コミット/PR の双方を漏れなく記録**する（上位設計が正本として正しくコード側の実装漏れ・誤認の場合は、上位設計書が正本であり改修不要である旨を明記する）。
> 3. 上位・関連設計および他コンポーネントへの影響波及を確認し、必要に応じて関連 Issue へ通知する。
