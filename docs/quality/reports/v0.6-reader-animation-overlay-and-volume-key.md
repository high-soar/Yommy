# Milestone `v0.6`（リーダーページ送りアニメーション・上下連動オーバーレイ＆シークバー・音量キー送り）品質分析・振り返りレポート（Kaizen）

## 1. エグゼクティブサマリー（Executive Summary）

Milestone `v0.6`（Reader Animation, Overlay & Hardware Key UX）では、Milestone `v0.5` で確立した縦書き 3 スロット水平スワイプラック・CSS マルチカラム組版を基盤として、読書体験のさらなる洗練を目指す 3 つの機能拡張 Issue（`#201`, `#202`, `#203`）および開発プロセス改善 Issue（`#209`）を完遂した。

1. **Issue #201（リーダーのページ送り水平スライドアニメーション実装、HO-26）**:
   - 画面左右端 20% タップおよび水平スワイプ離上（移動量 30% 以上または高速フリック）によるページ送り確定時に、`slideOffsetPx = ±pageWidth` へ 200ms `ease-out` で滑り込ませた後に `onPageChange` 確定と `transition: none` での `slideOffsetPx = 0` 瞬間リセットを行う **2 段階水平スライドアニメーション機構** を実装。
   - 200ms アニメーション実行中に連続タップ（高速連打）または新規ドラッグが行われた際、保留中のページ移動（`pendingTargetPage`）を即座に確定させてから次操作を開始し、入力の取りこぼしをゼロにした。
2. **Issue #202（リーダー上下連動オーバーレイ［作品名・サブタイトル表示＆目次導線］とページシークバーの実装、HO-27）**:
   - 下部オーバーレイ（`ReaderBottomOverlay`）と完全連動して上端からスライドインする上部オーバーレイ（`ReaderTopOverlay`）を新設し、作品タイトル・エピソードサブタイトルの 1 行固定省略表示（`truncate` により 100 文字超でも高さ不変）と、現在位置を即時保存（`flushBookmark`）して作品詳細・目次画面（`SCR-02`）へ戻る「← 目次」ボタン（`TR-06`）を実装。
   - 下部オーバーレイ上段に、縦書き右綴じの進行方向（右が 1 ページ目、左が最終ページ）に合致した RTL ページシークバー（`dir="rtl"`、実効 `paged` 時のみ表示）を実装し、オーバーレイを開いたまま連続して任意ページへジャンプ可能にした。
3. **Issue #203（ハードウェア音量キーによるページ送り・スクロール送り対応と設定画面 ON/OFF トグルの実装、HO-28）**:
   - 設定画面（`SCR-05`）の「表示・組版設定」セクションに「音量キーでページ送り」ON/OFF トグル（`enableVolumeKeyPaging`、初期値 `false`）を追加し、SQLite 永続化・失敗時ロールバックを実装。
   - Android ネイティブ層に `VolumeKeyPlugin.java` および `MainActivity.dispatchKeyEvent` インターセプトを実装し、リーダー表示中かつ設定 ON の間のみ `KEYCODE_VOLUME_DOWN` / `KEYCODE_VOLUME_UP` を捕捉して OS 音量バー表示を抑止しつつ Web 側 `VolumeKeyBridge` へイベント通知するアーキテクチャを構築。
   - リーダー画面（`SCR-03`）にて音量［ー］で次へ（2 段階水平スライドまたは約 85% 順方向スクロール）、音量［＋］で前へ移動、エピソード境界での 2 段階遷移（案内ヒント表示 → 2.5 秒以内再押下で前後話遷移）、およびオーバーレイ展開中の自動非表示を実装し、Playwright E2E シナリオ `SCN-06` を新設。
4. **Issue #209（プロセス改善：中間 MK Sub-issue PR および Milestone Step 2 PR の AI 自律マージ導入）**:
   - 人間のレビュー・マージゲートを「入口（Step 2 設計更新 PR）」と「出口（Step 4 最終 IT / 親 Issue クローズ PR、Milestone Step 3 最終承認 PR）」に集中させ、Task Completion Gate 1〜6 をすべて通過しエスカレーション条件に該当しない中間 MK Sub-issue PR をオーケストレーター AI が自律マージする運用へ移行。

全機能 PR マージ後、**Issue #204（Milestone `v0.6` 全体横断レビュー・品質分析・完了承認）** において、マルチモデル 4 オーケストレーター（`Claude Opus 5.5` / `Independent Reviewer` / `Gemini 3.8 Flash` / `Gemini 4 Argon`）による独立横断レビュー（Round 1: `R1-01`〜`R1-25`）および Android 実機 APK 検証（`HO-26`〜`HO-28` 精算、追加指摘 `R1-26` 摘出）を実施し、全 26 件（`R1-01`〜`R1-26`）の指摘事項を検出した。
Step 2（Sub-issue `#232`）および実機検証フィードバック対応において、全 26 件の是正（`syncEngine.test.ts` の固定日付時限爆弾排除、`VolumeKeyPlugin` の `load()` / `handleOnDestroy()` ライフサイクル初期化と契約テスト追加、`ReaderPage` の音量キー購読順序・Promise 例外保護、`syncScrollBoundaryState()` による連続スクロール初期/短文時の端到達フラグ同期、エピソード/モード切替時の 200ms スライドタイマー・境界状態リセット、リーダー再遷移時のマルチパス計測（初回 0px 幅解消・`hasUserChangedPageRef`）によるしおりページ位置復元の安定化［`R1-26`］、親 UT の `vi.spyOn` による直下の子 Props・コールバック検証への分離、`SCN-01`/`SCN-06` の E2E 検証強化、正本仕様書・差分仕様アーカイブ・バグ記録台帳の完全同期）を完遂し、全自動テスト（UT 1,557 件 / カバレッジ 100%、VRT 422 件、IT 13 件）の PASS を達成した。

### 3.2 傾向分析と考察

1. **Design (`D`) の抑制と実機レイアウト確定タイミングの知見（28.6%、製品コード `D` は 2 件）**:
   - Step 2 設計更新 PR（`#208`, `#218`, `#227`）における事前設計と独立 AI レビュー（`pr-reviewer`）が有効に機能し、製品コードにおける原因 `D` は連続スクロール初期表示・1 画面短文時の端到達判定考慮漏れ（No. 194: `R1-18`）と、リーダー再遷移時のマルチパス総ページ数計測におけるしおり進捗率復元考慮漏れ（No. 201: `R1-26`）の 2 件に抑えられた。
2. **Async (`A`: 28.6%) および State (`S`: 23.8%) の顕在化**:
   - `v0.6` では 200ms 水平スライドアニメーションタイマー（`#201`）と Android ネイティブ音量キーブリッジ（`#203`）を導入したため、以下のような **「状態遷移と非同期タイミングの境界」** に起因する指摘が中心となった：
     - スライドアニメーションの 200ms タイマー待機中に下部オーバーレイ等から別エピソードへ遷移した際、旧エピソードのタイマーが遅延発火して新エピソードのページ位置を上書きする競合（No. 195: `R1-19`）。
     - `ReaderPage` での `setVolumeKeyPagingEnabled(true)` 呼び出しと `addVolumeKeyListener` 登録の順序逆転、および Promise rejection 未捕捉（No. 193: `R1-04`, `R1-08`）。
     - `VolumeKeyPlugin.java` の `static volatile boolean volumeKeyPagingEnabled` が Activity 再生成や WebView リロード時にリセットされない状態残留リスク（No. 192: `R1-03`）。
3. **Time-bomb テスト（`B`: No. 191 `R1-01`）の早期摘出**:
   - `v0.4` で作成された `syncEngine.test.ts` の Tombstone 保持期限テストに固定日付（`2026-10-05`）が埋め込まれており、ちょうど 30 日経過した `2026-11-04` に GC パージ条件に達して失敗する「時限爆弾テスト」が顕在化した。現在時刻（`baseNow = Date.now()`）からの相対日時計算へ全面置換するとともに、テストガイドラインで固定過去日付ハードコードを恒久禁止した。

## 5. Milestone `v0.6` 固有の設計的知見と再発防止策（Kaizen アクション）

Milestone `v0.6` 横断レビュー（`R1-01`〜`R1-25`）および実機検証（`R1-26`）から得られた技術的教訓に基づき、`docs/guidelines/testing.md` および `.github/skills/c-ut-workflow/SKILL.md` に以下の 5 つの再発防止規律を恒久反映した。

### 5.1 テストにおける実時間依存（固定日付 Time-bomb）の排除規律（`R1-01` 再発防止）

- **課題**: `Date.now()` との差分で TTL（7 日間）や Tombstone 保持期限（30 日間）を判定するロジックのテストに `"2026-10-05T00:00:00.000Z"` のような固定カレンダー日付をハードコードすると、現実の日時経過とともにテストが突然失敗する時限爆弾（Time-bomb）となる。
- **対策**: `Date.now()` と比較する有効期限・保持期限テストでは固定過去日付文字列のハードコードを禁止し、必ず実行時点からの相対日時生成ヘルパー（`new Date(Date.now() - days * 86_400_000).toISOString()`）または `vi.setSystemTime` を使用するルールを `docs/guidelines/testing.md` §3.4 および `c-ut-workflow/SKILL.md` §2 に明記した。

### 5.2 Capacitor ネイティブプラグインの `static` 状態解放・契約テストと Bridge 購読順序（`R1-03`, `R1-04`, `R1-08`, `R1-12` 再発防止）

- **課題**:
  1. `MainActivity.dispatchKeyEvent` から参照するため `VolumeKeyPlugin` に持たせた `static volatile boolean volumeKeyPagingEnabled` が、プラグインの `load()` や `handleOnDestroy()` でリセットされないと、リーダー画面表示中に Activity 再生成（画面回転等）や WebView リロードが起きた際に `true` が残留し、リーダー外でも音量キーが消費され続ける恐れがある。
  2. Web 側（`ReaderPage`）で `setVolumeKeyPagingEnabled(true)` を `addVolumeKeyListener` より先に呼ぶと直後のキーイベントを取りこぼす可能性があり、また `void bridge.setVolumeKeyPagingEnabled(...)` として Promise rejection を未処理にすると Unhandled Rejection となる。
- **対策**:
  - Java プラグインの `static` フラグは必ず `load()` および `handleOnDestroy()` で初期値（`false`）にリセットし、その実装有無を `scripts/android-build-config.test.ts` の静的契約テストで機械検証する。
  - Web 側 Bridge 利用時は **`add*Listener` を先行登録してから有効化メソッドを呼び出し**、非同期 Bridge 呼び出しには `.catch(() => {})` を付与して Unhandled Rejection を防ぐ規律を `testing.md` §2.3 および `c-ut-workflow/SKILL.md` §2 に追加した。

### 5.3 アニメーションタイマー・スクロール境界 Ref の話数/モード切替時クリーンアップと操作開始時同期（`R1-18`, `R1-19` 再発防止）

- **課題**:
  1. 200ms スライドアニメーション中に `chapterIndex`（前後話遷移）や `isPaged`（モード切替）が変化すると、旧エピソードの `animationTimerRef` が遅延発火して遷移先のページ位置を上書きする。
  2. 連続スクロールモードで初期表示直後（`scroll` イベント未発火時）や 1 画面に収まる短文（`maxScroll <= 0`）のとき、`reachedStartRef` / `reachedEndRef` が更新されず音量キーやスワイプによる端 2 段階遷移が不発となる。
- **対策**:
  - `chapterIndex` または `isPaged` 変化時の `useEffect` で、進行中のアニメーションタイマー・境界ヒントタイマー・保留ページ参照・端到達 Ref（`false`）を一括リセットする。
  - 連続スクロール時は `syncScrollBoundaryState()` により各操作開始時（ポインター・タッチ・ホイール・音量キー）に実 DOM 座標および `maxScroll <= 0`（1 画面短文の両端到達判定）から `reachedStartRef` / `reachedEndRef` を同期評価する規律を `c-ut-workflow/SKILL.md` §2 に追加した。

### 5.4 Container / Page 単体テストの厳格な親子分離（`vi.spyOn` / `vi.mock`）と `SCN-xx` 正本トレーサビリティ（`R1-05`, `R1-11`, `R1-23` 再発防止）

- **課題**: `ReaderContainer.test.tsx`、`ReaderPage.test.tsx`、`SettingsContainer.test.tsx` 等で子・孫コンポーネント内部の DOM 要素を重複検証していたため、親子分離原則（鉄則 6）に反するだけでなく、CI マルチコア高負荷環境下で `onTotalPagesChange` や `popstate` しおり保存が非同期競合してタイムアウトを引き起こした。また新規追加した `SCN-06` 等が `screen-transitions.md` に一覧化されていなかった。
- **対策**:
  - Container / Page の単体テストでは `vi.spyOn`（または `vi.mock`）を用いて「親の状態管理と直下の子へ渡す Props / コールバック配線」のみを決定論的に検証し、子・孫の内部 DOM 検証は各子コンポーネント自身の UT に委譲する。
  - 新規結合テストシナリオ（`SCN-xx`）追加時は、`docs/specs/screen-transitions.md` §4 および対象機能仕様書（`docs/specs/features/*.md`）の E2E セクションへ必ず登録する規律を `testing.md` §1・§3 に明記した。

### 5.5 マルチパス DOM 計測（初回マウント・`requestAnimationFrame`・`document.fonts.ready`）における初期状態復元の冪等性規律（`R1-26` 再発防止）

- **課題**:
  1. `ReaderView` 初回マウント時の `useEffect` では `containerWidth` state が `0` のまま DOM 上のスロット幅が `0px` で描画されているため、スロット幅確定前に `content.scrollHeight` を計測すると 1 行 1 文字状態の過大な総ページ数（例: 20 ページ）が通知される。
  2. `useReader` の `setTotalPages` が単発フラグ（`isFirstPageMeasurementRef`）で最初の 1 回の通知だけで進捗率復元を打ち切っていたため、直後に正しい総ページ数（例: 5 ページ）が再通知された際に `prevPage > validTotal` のクランプ処理が走り、中間ページ（例: 2/5 ページ目）だった現在位置が最終ページ（5/5 ページ目）へ化けていた。また既存 IT（`SCN-01`）が全 2 ページの短文だったため、2 ページ目＝最終ページとなりクランプとの区別がつかず検出を逃していた。
- **対策**:
  - `ReaderView.measure()` では `currentWidth > 0 && currentHeight > 0` のとき計測対象 `content` 要素へ `style.width` / `style.height` を即時反映してから `scrollHeight` を読み取り、計測 `useEffect` の依存配列に `containerWidth` を含める。
  - `useReader` では単発フラグを廃止して `hasUserChangedPageRef` を導入し、ユーザーが手動ページ操作（`goToPage`）を行うまでの初期レイアウト・Web フォント確定期間中は、`setTotalPages` が複数回呼ばれても毎回 `initialScrollProgressRef.current` から `calculatePageFromProgress` で現在ページを再算出する。
  - ページ位置復元・クランプを検証する結合テスト（`SCN-01`）では、必ず **3 ページ以上（`totalPages >= 3`）の中間ページ（`1 < currentPage < totalPages`）** をテストデータとして使用する規律を `testing.md` §3.4 および `c-ut-workflow/SKILL.md` §2 に追加した。
