# レビューコメント記述仕様（SSOT）

本ドキュメントは、Yommy リポジトリにおける Pull Request（PR）レビューおよび節目（Phase 完了・ミニリリース Milestone 完了）の全体横断レビューにおいて、人間レビュアーおよび AI エージェントが使用するコメントフォーマットの正本（Single Source of Truth）です。

---

## 1. 基本原則

1. **事実と証拠に基づく記述（Evidence-based）**:
   - 変更差分（diff）、変更対象ファイルの全文、承認済み仕様・設計正本（`docs/specs/`）、開発規約（`docs/guidelines/`）、テストコード、または実行証跡に裏付けられた具体的な問題のみを報告します。
   - 個人のスタイルの好みや、根拠のない推測的リスクを欠陥（Defect）として報告してはなりません。
2. **重要度（Severity）の明記**:
   - 各指摘には `[P0]` 〜 `[P3]` の重要度を付与し、重要度の高い順に並べます。
3. **再現・修正に必要な 4 要素の網羅**:
   - すべての指摘には「対象箇所（`Location`）」「問題内容と発生条件（`Problem`）」「正本との齟齬・影響（`Impact`）」「具体的な修正案・引き継ぎ（`Recommendation`）」の 4 要素を必ず含めます。

---

## 2. 重要度（Severity）の定義

| 重要度     | 名称                     | 定義・判定基準                                                                                                                                                                      |
| :--------- | :----------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`[P0]`** | **致命的（Critical）**   | アプリのクラッシュ、ローカル DB データの破損・消失、重大なセキュリティ脆弱性（XSS 等）、CI/開発環境の完全破損など、即座に対処が必要な致命的欠陥。                                   |
| **`[P1]`** | **重大（High）**         | `docs/specs/` の受け入れ条件（`AC-xx`）やインターフェース/DB 契約の未達、主要機能の不全、Task Completion Gate 違反（カバレッジ未達・1対1 Story/UT 欠落・原因 `D` の設計未同期等）。 |
| **`[P2]`** | **通常・改善（Medium）** | 基本機能は動くが設計整合性・保守性・型安全性を損なう問題、境界値・異常系の考慮漏れ、ドキュメント間の記述不整合やリンク切れ、OKF フロントマター不備。                                |
| **`[P3]`** | **軽微（Low）**          | 将来の改善提案、軽微なタイポ・表記揺れ、可読性向上など、即座に修正しなくても動作や後続作業に影響を与えない事項。                                                                    |

---

## 3. 単一指摘（Finding）の共通フォーマット

PR のインラインレビューコメント、PR レベルの個別指摘、および Issue での指摘には以下の形式を使用します。

```markdown
### [重要度] 簡潔で具体的な要約

- **Location**: `path/to/file.ext:行番号`
- **Problem**: 不正な振る舞い・不整合な記述内容と、それが発生する条件。
- **Impact**: `docs/specs/` や `docs/guidelines/` との齟齬、システムや利用者への影響。なぜこれが誤りなのかの根拠。
- **Recommendation**: 具体的な修正方法、または後続 Issue（申し送り `HO-xx`）への引き継ぎ案。
```

> [!NOTE]
> 本リポジトリでは日本語での記述を標準とします。4要素のキー名（`Location`, `Problem`, `Impact`, `Recommendation`）はそのまま維持してください。

## 4. PR レビューコメントの運用ルール

### A. インラインレビューコメント

- 該当する変更差分行に直接アンカーして、上記「3. 単一指摘の共通フォーマット」で投稿します。

### B. PR 全体レビューコメント（PR レベル）

- 差分行に直接紐付けられない指摘（ファイル全体の整合性や別ファイルとのトレーサビリティ漏れ等）がある場合、または指摘事項が 0 件の場合に PR レベルのコメントとして投稿します。
- **指摘なし（合格）の場合のテンプレート**:
  ```markdown
  ## レビュー結果

  - **確認範囲**: （対象 PR の変更ファイルおよび照合した `docs/specs/`・`docs/guidelines/`）
  - **実行した検証**: `npm run typecheck`, `npm run lint`, `npm run test:coverage`, `npm run test:vrt` 等
  - **判定**: Actionable な指摘事項はありません。
  ```

### C. レビューコメントスレッドの返信と収束（Resolve）

- **実装者（Author / Worker）**: 各指摘スレッドに対し、修正コミット（SHA）と検証結果（原因 `D` の場合は設計書同期修正コミットを含む）、または対応しない妥当な理由を返信します。
- **レビュアー（`pr-reviewer`）**: 最新コミットとテスト結果を確認し、修正が確認できたスレッドのみを解決（Resolve conversation）します。未検証のままスレッドを閉じてはなりません。
- **権限境界**: AI レビュアーはコメント投稿・返信・確認済みスレッドの Resolve のみを行い、PR の Approve や Merge は行いません（最終承認・マージは人間が行います）。

## 5. 節目横断レビュー（Phase / ミニMilestone 完了レビュー）の集約形式

複数の成果物を横断検証する節目レビュー（Issue コメント）では、複数回のレビュー（Round 1, Round 2...）における指摘 ID の衝突を防ぎ、人間が迅速にトリアージできるよう以下の採番規則と集約フォーマットを使用します。

### 5.1 指摘 ID（Finding ID）の採番ルール（ラウンドプレフィックス方式）

- **ID 形式**: `R<ラウンド番号>-<2桁連番>`（例: 初回は `R1-01`, `R1-02`、2回目は `R2-01` 等）
- **マルチモデル・複数オーケストレーターによる追記スレッド規律**:
  - 横断レビューにおいて、モデルの違い（Flash, Pro, Claude 等）による着眼点の差や多様な検証結果を個別に把握できるよう、各オーケストレーターは独立したレビューコメント（追記スレッド）として投稿します。
  - **既存コメントの事前確認義務**: オーケストレーターはコメント投稿前に必ず Issue 上の既存コメントを取得・確認し、既に投稿されている最新の指摘 ID（例: `R1-16`）を確認します。
  - **ID 連番の継続（衝突の厳禁）**: 先行コメントに既に指摘が存在する場合、自身のコメント内の新規指摘は先行コメントの最終連番を引き継ぎ、連続した ID（例: `R1-17`, `R1-18`...）で採番します。同一ラウンド内で同一の ID を重複して使用してはなりません。
  - **先行指摘との重複時の記述**: 先行オーケストレーターと同一の不備を検出した場合は、無駄な ID の二重採番を避け、「先行指摘 `R1-01` を追認・補強」として言及するか、異なる視点・影響度がある場合のみ新 ID として起票します。
- **再レビュー時（Round 2 以降）の扱い**:
  - 新たに発見された指摘には、当該ラウンドのプレフィックス（`R2-01` 等）を採番します。
  - 前回ラウンドで未解消の指摘を再掲・追跡する場合は、新しい ID を振らず **初出時の ID（`R1-01` 等）を維持** してステータスを記載します。

### 5.2 横断レビュー集約コメントのテンプレート

```markdown
## 横断レビュー結果（Round N - レビュアー / モデル名）

- **対象フェーズ / Milestone**: （例: Phase 3 PoC / Milestone v0.1）
- **レビュアー種別 / 使用モデル**: （例: オーケストレーター #2 [Gemini 3.8 Pro] / サブエージェント観点別検証）
- **対象成果物**: （例: `docs/specs/`, `src/`, `test/it/`, `docs/quality/bug-and-handover-log.md`）
- **対象 SHA**: `<commit-sha>`
- **確認した完了条件・ゲート**: （例: 要望 Issue #1〜#4 の完了、全テスト・VRT・カバレッジ 100% PASS）
- **実行したチェック**: （例: 独立サブエージェントによる観点別検証、静的検査・テスト実行確認）
- **先行コメントとの関係**: （例: 初回投稿 / コメント #1 [ID: R1-01〜R1-16] の追認および R1-17 以降の新規指摘起票）
- **未確認事項**: （例: 人間による実機最終確認・Milestone 承認は未実施）

### 指摘一覧サマリー

| ID    | 重要度 | 対象成果物 / ファイル                       | 要約                                                       | 状態 |

| R1-18 | P2     | `docs/specs/screen-transitions.md:30`       | `TR-04` の遷移条件記述の揺れ                               | Open |

---

- **Problem**: ...
- **Impact**: ...
- **Recommendation**: ...
```
