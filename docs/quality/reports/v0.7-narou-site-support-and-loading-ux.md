# Milestone `v0.7`（小説家になろう対応 ＆ WebアクセスローディングUX改善）品質分析・振り返りレポート（Kaizen）

## 1. エグゼクティブサマリー（Executive Summary）

Milestone `v0.7`（Narou Site Support & Web Access Loading UX）では、初期 MVP 以来の「カクヨム」単一サイト対応からマルチサイト対応への第一歩として、国内最大級の小説投稿サイトである **「小説家になろう（`narou`: `ncode.syosetu.com`）」への全面対応**、およびモバイル通信環境下における読書・探索の快適性を担保する **「Webアクセス時ローディング状態明示UX改善」** の 3 つの親 Issue（`#238`, `#239`, `#240`）を完遂した。

1. **Issue #238（Webアクセス発生時のローディング状態明示UX改善、HO-30）**:
   - ランキング集計期間・ジャンル切替、検索条件変更、および小説リーダーでの未キャッシュ話遷移（`goToChapter`）時において、インラインスピナー・ローディングメッセージを明示し、通信中のピル・セレクター非活性化（二重実行抑止）を実装。
   - `ReaderPage` における話数遷移ローディング状態（`isNavigatingChapter`）のインジケーター表示（`AC-RD-28`）を整備。
2. **Issue #239（小説家になろう［narou］パーサーおよび複数ページ目次取得・クラウド同期対応、HO-29）**:
   - `NarouParser` を新設し、なろう HTML（作品情報・複数ページ目次・本文組版）のスクレイピングロジックを実装。前書き（`novel_p`）・本文（`novel_honbun`）・後書き（`novel_a`）・区切り線、ルビ（`<ruby>`）、傍点（`<em class="bouten">`）の縦書き組版抽出に対応（`AC-NR-01`〜`10`）。
   - 100話を超える長編作品に対応するため、`nextTocPageUrl` を追跡する複数ページ目次取得パイプライン（`fetchFullNovelIndex`：上限100ページ安全停止・SSRF防止・循環参照ガード付き）を構築し、Google Drive クラウド同期（`SyncEngine`）のマルチサイト対応を実現。
3. **Issue #240（小説家になろうの検索・ランキング対応と探索画面サイト切替［SiteSelector］の実装、HO-29）**:
   - なろう小説 API（JSON）を用いた検索・ランキング取得パーサー（`searchNovels` / `fetchRanking`）を実装し、カクヨムの大ジャンル体系となろうの独自ジャンル・小ジャンル体系を相互変換する `genres.ts` マッピングを整備。
   - 検索画面（`SCR-06`）およびランキング画面（`SCR-07`）上部にサイト切替 UI（`SiteSelector`）を配備し、サイト切替時のジャンルピル動的連動・一覧自動再取得・ページネーション（`loadMore`）のシームレスな切替を実現。結合テスト `SCN-02` になろう探索・本棚追加・リーダー読書の E2E シナリオを追加。

全機能 PR マージ後、**Issue #241（Milestone `v0.7` 全体横断レビュー・品質分析・完了承認）** において、マルチモデル 3 オーケストレーター（`Claude Opus 5.5` / `Gemini 3.8 Flash` / `Gemini Pro`）によるアンカリング防止型独立横断レビュー（Round 1: `R1-01`〜`R1-24`）を実施した。
Step 2（Sub-issue `#259` / PR `#260`）において全 24 件の指摘事項（`useReader` アンマウントガード `R1-18`・`fetchFullNovelIndex` 統一 `R1-19`、検索/ランキングのリクエスト世代カウンタおよび `loadMore` 競合ガード `R1-01`、IT アサーション強化 `R1-02`/`R1-06`/`R1-24`、正本仕様書の双方向トレーサビリティ補強 `R1-03`〜`R1-23` 等）を自律マージにて網羅的に是正した。さらに CI 安定化 PR（`#262` / No. 233：`useReader` の `novelRef` 非同期競合解消）および Android 実機検証（`HO-29`, `HO-30`）を完全収束させ、全自動テスト（UT 1,706 件 / カバレッジ 100%、VRT 446 件、IT 15 件）の PASS を達成した。

## 5. Milestone `v0.7` 固有の設計的知見と再発防止策（Kaizen アクション）

Milestone `v0.7` 横断レビュー（`R1-01`〜`R1-24`）および CI 是正（No. 233）から得られた教訓に基づき、`docs/guidelines/testing.md` および `.github/skills/c-ut-workflow/SKILL.md` に以下の 4 つの再発防止規律を恒久反映した。

### 5.1 `useReader` における非同期参照・同期反映規律（No. 233, `R1-18`, `R1-19` 再発防止）

- **課題**:
  1. `useReader` の `loadInitialData` および `fetchNovelFromUrl` において、`setNovel(loadedNovel)` を呼び出した後、`novelRef.current` が `useEffect([novel])` を通じて遅延更新される設計となっていた。このため、初期ロード直後にスクロール進捗更新コールバック（`onScrollProgressChange`）が発火した際、`novelRef.current` が `null` と判定され、しおり保存（`updateBookmark`）がスキップされる非同期競合（CI Flakiness）が発生した（No. 233）。
  2. `goToChapter` および `fetchNovelFromUrl` において、通信中にコンポーネントがアンマウントされた際のガード（`isMountedRef`）が欠落しており、画面離脱後に不要な DB 更新や未閲覧話の既読化が走る潜在リスクがあった（`R1-18`）。
  3. `fetchNovelFromUrl` で直接パーサーを呼び出していたため、101話以上のなろう作品で1ページ目しか取得されない不整合があった（`R1-19`）。
- **対策**:
  - `loadInitialData` および `fetchNovelFromUrl` では、`setNovel` と同時に **`novelRef.current` および `currentChapterIndexRef.current` を同期的（インライン）に更新** する。
  - `updateScrollProgress` および `flushBookmark` では、**`novelRef.current ?? novel` のフォールバック参照** を行い、コミットラグによる保存漏れを 100% 防止する。
  - すべての非同期取得処理において `if (!isMountedRef.current) return;` を徹底し、Web 小説の全話インデックス取得は必ず `fetchFullNovelIndex` に一本化する。

### 5.2 非同期探索・ページネーションにおけるリクエスト世代ガードと UI 相互排他（No. 209: `R1-01` 再発防止）

- **課題**:
  - 検索画面およびランキング画面において、`loadMore`（次ページ取得）の非同期通信中に、ユーザーが別サイト（`SiteSelector`）への切り替えや検索条件・集計期間ピルの変更を行った場合、遅延解決した旧リクエストの結果が新条件の一覧に混入・上書きされる競合リスクが存在した。
- **対策**:
  - 各探索 Hook（`useNovelSearch`, `useNovelRanking`）に `requestIdRef`（世代カウンタ）を導入し、通信完了時に発行時点の最新リクエスト ID と一致するかを検証するガードを必須とする。
  - 画面側（`SearchPage`, `RankingPage`）において、`isLoading || isLoadingMore` 通信中は `isInteractingDisabled` フラグにより、サイトセレクターおよび条件ピル操作を UI レベルで非活性化（二重実行抑止）する規律を確立した。

### 5.3 結合テスト（IT）における実体アサーション徹底（No. 206, 207, 210, 216, 232: `R1-02`, `R1-08`, `R1-24` 再発防止）

- **課題**:
  - 結合テスト（`test/it/`）において、`if (await element.isVisible())` のような条件付きアサーション（非表示時に暗黙スキップされる偽陽性リスク）、操作前から既に可視な一覧コンテナ要素の `toBeVisible()` だけで済ませる検証漏れ、および固定待機 `waitForTimeout` の残存が横断レビューで複数指摘された。
- **対策**:
  - 結合テストでの条件分岐スキップは固く禁止し、`toBeVisible()` 等で対象要素の存在・可視性を明示的にアサートする。
  - フィルタ・ピル切替時は、一覧の可視性だけでなく `toHaveAttribute("aria-pressed", "true")` や `toHaveValue(...)` による **「UI 選択状態の反映」を必ず検証** する。
  - 外部サイトパーサーの結合検証では、単なるテキスト表示にとどまらず、ルビ（`<ruby>`）、傍点（`<em class="bouten">`）、区切り線（`<hr>`）、前書き・後書きの実レンダリングを E2E で確実に検証する。

### 5.4 正本仕様書・OKF フロントマターの 3 点双方向トレーサビリティ同期（No. 202, 204, 211, 217, 218 等再発防止）

- **課題**:
  - 新機能追加や受入条件新設時（`AC-NR-xx`, `AC-RD-28` 等）に、全体要件（`requirements.md` §3/§4）、画面遷移（`screen-transitions.md` §4）、および機能仕様書（`features/*.md`, `parsers/*.md`）の間で、一部のドキュメントのみが更新されトレーサビリティのリンクが非対称となる事象が多発した。
- **対策**:
  - 新規要件・受入条件の追加時は、**「① `requirements.md`（機能一覧 ＆ ロードマップ表）」「② `screen-transitions.md`（遷移表 ＆ E2E シナリオマッピング）」「③ 個別仕様書（`features/*.md` / `parsers/*.md`）」の 3 点セットで同時に双方向リンクを更新** する規律を徹底する。
  - OKF YAML フロントマターの `tags`, `related_specs`, `related_tests` も相互に対称性を確認し、`validate-okf.mjs` による機械検証をマージ前必須とする。
