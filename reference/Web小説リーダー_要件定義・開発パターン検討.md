# Web小説リーダーアプリ 要件定義・開発パターン検討書

## 1\. プロジェクト概要

AI駆動開発（仕様駆動開発・テスト駆動開発）を活用し、VS CodeをメインエディタとしてAndroid向け「Web小説リーダーアプリ」を開発する。 複数のWeb小説サイトのスクレイピング、ローカルキャッシュ、小説特化のビューワー表示、およびサイト側の仕様変更に強いブラウザ連携機能を備える。

---

## 2\. 要件定義

### 2.1 コア機能要件（基本要件）

- **Webスクレイピングとローカルキャッシュ**  
  - 指定したWeb小説のURLから目次・各話本文を取得し、端末内のローカルストレージ（DB）に保存する。  
  - オフライン環境でもキャッシュ済みエピソードを快適に閲覧できる。  
- **見やすい形式でのリーダー表示**  
  - 取得した本文データを整形し、読書に最適化されたレイアウトで表示する。  
- **複数ページ（複数話・複数サイト）への対応**  
  - 連載小説の複数話一括取得・連続閲覧に対応する。  
  - 複数のWeb小説サイト（小説家になろう、カクヨム、ハーメルン等）の構造に対応する。  
- **ブラウザ表示（フォールバック機能）**  
  - 対象サイトの急なDOM構造変更、Cloudflare等のボット対策、またはログイン必須ページに対応するため、アプリ内ブラウザ（WebView）で直接ページを表示できる。  
- **キャッシュ管理機能**  
  - 作品ごとのキャッシュ容量確認、既読エピソードのキャッシュ削除、一括クリア機能を提供する。

### 2.2 追加推奨要件（実用性・保守性向上）

- **レートリミット制御とバックグラウンドダウンロードキュー**  
  - 複数話の一括取得時、対象サーバーへの過度な負荷やIP BAN（503エラー等）を防ぐため、リクエスト間隔のウェイト制御（例：1〜2秒間隔）とキュー管理を行う。  
- **アダプター方式のパーサーとWebView DOM抽出連携**  
  - サイトごとの解析ルールを分離（Strategyパターン）。  
  - 万が一バックグラウンド取得が失敗した場合、内蔵WebViewで人間がページを開き、表示中のDOMから直接本文を抽出してキャッシュDBへ取り込む「ブラウザ経由インポート機能」を搭載する。  
- **小説特化型組版・UI機能**  
  - **ルビ（`<ruby>`タグ）および傍点の正確なレンダリング**。  
  - **縦書き / 横書きの切り替え**、フォントサイズ、行間、余白のカスタマイズ。  
  - **カラーテーマ切り替え**（白背景、セピア、ダークモード、有機EL向け純黒モード）。  
  - **しおり・自動スクロール位置保存**、音量キー等によるページめくり操作。  
- **更新チェック（差分取得）とデータバックアップ**  
  - お気に入り登録した小説の最新話チェックと未取得話の差分ダウンロード。  
  - 読書履歴・しおり・キャッシュデータのエクスポート / インポート機能。

## 3\. 開発パターンの比較検討（VS Code × AI駆動開発）

Androidネイティブ（Kotlin / Jetpack Compose）をVS Code単体で開発する場合、Gradle同期やUIプレビュー、LSPの安定性に難がありAndroid Studioの併用が必須となる。また、ネイティブUIコンポーネントでの「縦書き・ルビ表示」の自作は非常にコストが高い。 そのため、**VS Codeで完結しやすく、CSSによる高度な組版（縦書き・ルビ）とAIのコード生成能力を最大限に活かせるクロスプラットフォーム構成**を推奨する。

| 開発パターン | 総合適性 | スクレイピング・DOM解析 | 小説ビューワー表現 (縦書き/ルビ) | VS Code × AI駆動の快適さ |
| :---- | :---: | :---- | :---- | :---- |
| **① Capacitor \+ React (Vite / Next.js)** | **◎ 最適** | WebView連携やJS標準のDOMParserがそのまま使えて強力 | **最強**（CSSの `writing-mode: vertical-rl` や `<ruby>` がそのまま使える） | **最高**（通常のWeb開発と完全に同じ。ブラウザで9割デバッグ可能） |
| **② React Native (Expo)** | **◯ 良好** | `cheerio` 等の軽量パーサー＋`react-native-webview` で実装可能 | ネイティブTextは縦書き・ルビに弱い（リーダー画面のみローカルHTMLをWebView表示するハイブリッド構成が定石） | **最高**（Expo Go / Dev Clientで実機確認が高速） |
| **③ Flutter (Dart)** | **◯ 良好** | `html` パッケージ等で実装可能 | 縦書き・ルビは専用パッケージや自前描画が必要でやや手間 | **良好**（VS Code拡張が優秀だが、Web系に比べると縦書き組版の調整コストが高め） |
| **④ Kotlin \+ Jetpack Compose** | **△ 非推奨** | `Jsoup` という優秀なライブラリがある | 縦書き自作が困難。結局リーダー部はWebViewに頼りがち | **厳しい**（VS Code単体では開発しづらく、Android Studio併用が前提） |

## 4\. 推奨アーキテクチャとAI駆動開発の進め方

### 4.1 推奨技術スタック

- **パターンA（Web技術統一・組版重視）**: **React (TypeScript / Vite) \+ Capacitor**  
  - アプリ全体をWeb技術で構築し、CapacitorでAndroidネイティブアプリとしてラップする。縦書きやルビ、WebView連携が最もシンプルに実装でき、WSL2 \+ VS Code環境でも通常のWebアプリとして高速に開発・テストが可能。  
- **パターンB（ネイティブ操作感重視）**: **React Native (Expo) \+ WebView（リーダー画面のみ）**  
  - 本棚画面やキャッシュ管理画面はReact Nativeのネイティブコンポーネントでサクサク動かし、小説本文のリーダー画面（およびブラウザ表示画面）のみ `react-native-webview` を使ってHTML/CSSでレンダリングする。

### 4.2 AI駆動開発（仕様駆動・TDD）を活かす3層モジュール設計

AIエージェント（Claude CodeやGitHub Copilot）にコンテキストを渡しやすくするため、以下の3層を明確に分離して開発を進める。

1. **Parser Layer（スクレイピング・DOM解析層）**  
   - **設計**: サイト別のアダプター（`NarouParser`, `KakuyomuParser`, `GenericFallbackParser` など）を共通インターフェース `NovelParser` で実装する。  
   - **TDDアプローチ**: 対象サイトのサンプルHTMLをテストフィクスチャとしてローカルに保存し、「HTMLを入力として、小説タイトル・目次リスト・整形済み本文HTML（ルビ保持）を返す」ユニットテスト（Vitest / Jest）を先に作成。サイト側の仕様変更時も、新しいHTMLをテストに追加してAIにセレクタ修正を指示するだけで即座に復旧できる。  
2. **Storage Layer（ローカルDB・キャッシュ管理層）**  
   - **設計**: 数千話規模のテキストデータを高速に扱うため、SQLite（`@capacitor-community/sqlite` または `expo-sqlite`）を採用する。  
   - **主要テーブル**:  
     - `novels`: 作品ID、サイト種別、URL、タイトル、著者、総話数、現在のしおり位置、最終更新確認日時  
     - `chapters`: エピソードID、作品ID、話数インデックス、サブタイトル、URL、本文HTML（キャッシュ）、取得日時、既読フラグ、データサイズ（Byte）  
     - `download_queue`: キューID、対象URL、ステータス（待機中/取得中/完了/エラー）、リトライ回数  
3. **Viewer & WebView Bridge Layer（表示・ブラウザ連携層）**  
   - **設計**: キャッシュ済みHTMLにユーザー設定（縦書き/横書き、フォントサイズ、テーマ色）のCSSを適用して描画するビューワーと、ライブのWebページを表示する内蔵ブラウザを切り替える。  
   - **フォールバック連携**: 内蔵ブラウザ（WebView）にカスタムJavaScriptを注入（Inject）し、現在ブラウザで表示しているページのDOMを直接キャプチャしてParser Layerへ渡し、ローカルキャッシュへ保存できるブリッジ機能を実装する。
