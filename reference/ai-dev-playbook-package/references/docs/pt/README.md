## 1. 工程の目的と基本方針

### 1.1 目的

先行する C・UT（単体テスト: 94 files / 800 tests 100% PASS、ラインカバレッジ 90.65%）および IT（結合テスト: 15 files / 92 tests 100% PASS）により、個別コンポーネントおよび画面間・API連携の機能ロジックが仕様通り動作することは機械的に検証済みです。

本 PT（受入・総合テスト）工程では、本番相当環境（受入プレビュー環境 `npm run build:preview` + `npm run preview`）および実ブラウザ環境において、社内利用者の視点に立ち以下の事項を総合的に確認・評価し、Step 2 プロジェクト全体の完了およびリリース可否の判断材料とすることを目的とします。

1. **システム受け入れ条件（SYS-AC-01〜SYS-AC-14）の適合性検証**:
   - 外部設計書（`docs/ed/01-system-overview.md` §5.1）に定義された全 14 件のシステム受け入れ条件、および全 6 画面（SCR-AUTH, SCR-00〜04）の画面受け入れ条件を網羅する一連の業務フローが、実ブラウザ上で円滑に操作・完結できること。
2. **ロール別アクセス制御（RBAC）と業務通しシナリオの検証**:
   - 一般ユーザー（自プロジェクト限定、起票・対応・更新・コメント）および管理者ユーザー（全社横断閲覧・監査、ユーザー/プロジェクト管理、詳細閲覧専用）の職務分掌（SoD）に基づき、各ロールの業務フローが一貫して遂行できること。
3. **非機能要件・品質特性の合否判定基準適合性検証**:
   - 本番クリーンビルド成果物のアセット品質（判定基準: 各JSチャンク < 100.0 kB / CSS < 8.0 kB / 合計 < 120.0 kB [目標 < 90.0 kB]、DCE によるモックコード完全除外）、主要 6 画面の Lighthouse 監査（Performance $\ge 90$、Accessibility $\ge 90$ 等）、アクセシビリティ（キーボード操作性・フォーカス可視性・コントラスト比）、およびレスポンシブ視覚整合性（PC 1280px / タブレット 768px / モバイル 375px）が判定基準を満たすこと。
4. **結合テスト（IT）申し送り事項（PT-HO-01〜PT-HO-05）の実機検証**:
   - JSDOM 環境では原理的に検証が完結しなかったブラウザ実環境固有の動作（Service Worker 初期化競合、管理者専用 API インターセプト、401 トークン失効時のセッション破棄・リダイレクト・トースト通知、500 エラー時のインライン警告と再試行復旧、実画面幅でのアニメーション・CSS レンダリング）を実機で完全に検証・合否判定すること。
5. **不備記録の継続と総合欠陥除去率（Total-DRE）による品質評価**:
   - C・UT / IT 工程で確立された不備記録標準（スリム化必須6項目）を継承し、AI 作業中に確認された不備を製品コードと支援成果物に分離して記録する。工程完了時には総合欠陥除去率（$\text{DRE (Total)}$、目標 95% 以上）を算定し、品質分析・評価レポート（`docs/pt/quality/step2.md`）を作成すること。

### 1.2 基本開発原則（PT 標準）

- **ハイブリッド受入構成の徹底**:
  回帰テストおよび詳細な機能分岐・非同期競合制御は、CI 上で稼働する UT（800 tests）、IT（92 tests）、VRT（236 tests）で機械的に 100% 保証します。PT 工程では過剰な E2E 自動化コードの重複実装を避け（YAGNI 原則）、**実ブラウザでの業務受入チェック**に集中し、視覚的なレイアウト整合性、操作感、およびユーザー体験を人間視点で総合確認します。
- **本番クリーンビルドによるアセット品質保証**:
  通常の本番ビルド（`npm run build`）においてモックコードを完全除外（Dead Code Elimination: DCE）し、実バックエンド接続を想定したクリーンな本番バンドルサイズ（目標値: gzip < 90.0 kB、許容上限: gzip < 120.0 kB、DCE 達成）を主たるフロントエンド品質の判定根拠とします。
- **受入プレビュー環境（`mode: preview`）による実ブラウザ受入の実施**:
  受入テストの実施には、先行技術検証（`docs/pt/tech-verification.md`）で確立したプレビュー用ビルド（`npm run build:preview` + `npm run preview`）を使用し、実ブラウザ上で Service Worker によるモック API インターセプトを介した受入シナリオを実施します。
- **客観的レポート採取（Headless Chromium + Lighthouse CLI 方式）**:
  DevContainer 環境内での監査自動化・完全な実行再現性担保および客観的レポート生成（HTML/JSON）のため、公式な測定方式として Headless Chromium + Lighthouse CLI を採用します。
- **合否判定基準の厳格な適用と人による承認**:
  非機能要件の閾値（バンドルサイズ、Lighthouse スコア、アクセシビリティ基準）に対する合否判定を行い、すべての結果をエビデンスとして記録した上で、最終的な完了・承認判定（Issue #187）は人間レビュアーが行います。AI は人に代わって承認・クローズしません。

### 1.3 前Step開発範囲の包含・進化とシステム全体受入保証方針（PT標準）

本プロジェクトにおける受入・総合テスト（PT）は、Step 2 で新規追加された機能のみを局所的に確認するのではなく、**Step 1 から継承された全機能（一覧表示、詳細閲覧、検索・絞り込み、ステータス/担当者更新、コメント追加、ブラウザバック復元）を Step 2 のアーキテクチャ（認証必須化、RBAC、プロジェクト制、開閉サイドバー、Dirty Guard）に合わせて包含・進化させたシステム全体の統合業務受入** として実施します。

## 5. 不備記録および総合品質評価標準（Total-DRE）

### 5.1 不備記録の継続（スリム化必須6項目）

C・UT 工程および IT 工程で確立された「スリム化必須6項目」による不備記録標準を継承し、AI 作業中に確認された不備を製品コードと支援成果物（受入仕様書・測定スクリプト・エビデンス等）に明確に分離して `docs/pt/evidence/pt-bug-record.md` に記録します。

| 必須項目 | 項目名                   | 記載ルール                                                                                                                     |
| :------: | :----------------------- | :----------------------------------------------------------------------------------------------------------------------------- |
|    1     | **No.**                  | 当該タスク内での連番（1, 2, ...）                                                                                              |
|    2     | **検出手段**             | 不備が最初に確認された手段（例: `手動ブラウザ受入`, `Lighthouse CLI`, `バンドルサイズ分析`, `AIレビュー`, `静的検査` 等）      |
|    3     | **成果物区分**           | `製品コード` または `テスト・モック等支援成果物`（仕様書、スクリプト、エビデンス等）                                           |
|    4     | **対象箇所**             | 不備が存在したファイル名・関数名・モジュール名・仕様書節名                                                                     |
|    5     | **原因分類**             | 原因分類コード（L / S / D / B / A）                                                                                            |
|    6     | **不備の概要と是正内容** | 不備の具体的な現象・根本原因、およびどのように是正したか（コミットリンク・PRリンクを含む）を簡潔に記述する（マークダウン形式） |

#### 原因分類コード（5分類）

- **L (Logic)**: ロジック誤り（条件分岐ミス、ループ誤り、真偽値反転、フィルタリング・ソート計算ミス）
- **S (State)**: 状態遷移誤り（React state 更新漏れ、Context 値の不整合、ブラウザ履歴・URL クエリ同期ミス、ライフサイクル）
- **D (Design)**: 設計・仕様誤認（OpenAPI 契約や ED/ID 設計書の見落とし、パス・パラメータ・型不一致、認可権限誤認、シードデータ不整合）
- **B (Boundary)**: 境界値未考慮（`null` / `undefined` の考慮漏れ、空文字・空配列、最大文字数超過、極端な解像度での崩れ）
- **A (Async)**: 非同期制御不備（Promise ハンドリング漏れ、Service Worker 初期化競合、Race Condition、遅延レスポンス上書き）

### 5.2 総合欠陥除去率（Total-DRE）の算定基準

総合テスト（PT）工程完了時には、開発ライフサイクル全体を通じた品質保証能力を評価するため、総合欠陥除去率（$\text{DRE (Total)}$）を算定します。

$$\text{DRE (Total)} = \frac{\text{UT製品コード不備} + \text{IT製品コード不備}}{\text{UT製品コード不備} + \text{IT製品コード不備} + \text{PT製品コード不備}} \times 100\%$$

- **品質目標**: **$\text{DRE (Total)} \ge 95.0\%$**
- **先行工程の実績値（承認済み正本: `docs/c-ut/quality/step2.md`, `docs/it/quality/step2.md`）**:
  - 単体テスト（UT）工程不備件数: **36 件**（製品コード不備 **23 件** / 支援成果物不備 13 件）
  - 結合テスト（IT）工程不備件数: **9 件**（製品コード不備 **0 件** / 支援成果物不備 9 件）
  - 先行工程製品欠陥除去合計 (UT+IT): **23 件**（全不備ベース: $36 + 9 = 45$ 件）
- **PT 許容不備件数**:
  - **製品コードベース**: PT 工程で検出される製品コード不備が 1 件以内の場合: $\frac{23}{23 + 1} \times 100\% = 95.8\% \ge 95.0\%$（目標達成、0件なら 100.0%）
  - **全不備ベース（参考）**: PT 工程で検出される全不備が 2 件以内の場合: $\frac{45}{45 + 2} \times 100\% = 95.7\% \ge 95.0\%$（目標達成、1件なら 97.8%）
