## 1. 背景・目的

### 1.1 業務・技術背景

Step 1 では単一チーム内での問い合わせ受付・更新・コメント共有を完遂し、Step 2 では複数プロジェクト対応、ロールベースアクセス制御（RBAC）、職務分掌（SoD）、ダッシュボード、起票、ユーザー・プロジェクト管理、開閉式サイドバー、および画面離脱防止（Dirty State ガード）といったエンタープライズ業務フロントエンド機能を完遂しました。

Step 3 では、既存の業務機能や画面の振る舞いを 100% 維持した上で、以下の 3 点を主軸にシステム基盤と品質保証体系を進化させます。

1. **Next.js (App Router) への移行**:
   - 従来の Vite + 自前ルーティング構成から、エンタープライズ Web 標準である Next.js (App Router) へ移行します。
   - ディレクトリ構造に基づくファイルベースルーティング（`src/app/**/page.tsx`、`layout.tsx`、`not-found.tsx`）、ネストレイアウト、およびルート別自動コード分割（Route-based Code Splitting による初期ロード 100.0 kB 未満の達成）を導入します。
   - 既存の画面・コンポーネント（`src/features/`、`src/shared/`）および業務ロジックの振る舞いを維持し、利用者にデグレを感じさせないシームレスな移行を実現します。
2. **コンテナイメージによる画面提供と別コンテナ Mock API 接続の技術検証**:
   - 画面を Next.js コンテナイメージとして提供し、環境差異のない可搬性とデプロイ容易性を確保します。
   - リリース相当の接続確認や総合テスト（PT）において、OpenAPI 契約（`docs/ed/api/openapi.yaml`）と既存モックデータ（`src/mocks/db/`）を活用する Mock API サーバーを別コンテナで提供し、画面から本番想定の `/api` 経路（Rewrites またはリバースプロキシ等）で接続するネットワーク構成を技術検証します。
3. **UT / IT / PT の責務分離と品質保証体系の刷新**:
   - **UT（単体テスト）**: 「テストケース作成ルールの単純化」と「ソースコードとテストの 1 対 1 比較による人間レビューの容易化」を最優先とし、全 `.tsx` に対する `.stories.tsx` 必須化、`.test.tsx` 補完、親子分離（親の試験で子のバリエーションを兼ねない）、C0/C1 100% 網羅、および VRT（Playwright VRT）の UT（Storybook）への一本化を実施します。
   - **IT（結合テスト）**: Playwright Test（実ブラウザ駆動）へ移行し、画面単位のふるまい・画面遷移・異常系などの結合挙動を検証するとともに、全ケースでトレース（`trace: "on"`）を常時記録して DOM・画面・ネットワーク通信・コンソールログの監査証跡を残します（IT での VRT は廃止）。
   - **PT（総合テスト）**: 本番相当コンテナ環境（Next.js 画面コンテナ ＋ Mock API コンテナ）での実ブラウザ手動業務受入、初期 JavaScript バンドルサイズ 100.0 kB 未満の達成検証、非機能・品質特性検証（Lighthouse 監査、キーボード操作性、WCAG 2.1 AA コントラスト比、1280px / 375px レスポンシブ表示確認と証跡取得）、および Total-DRE（総合欠陥除去率）の品質分析を継続します。

### 1.2 業務目的

本システムは、Step 2 で確立したプロジェクト制と RBAC/SoD を堅持しつつ、以下の業務目的を達成します。

- **業務運用の安定性と継続性**: 一般ユーザーによる日々のチケット起票・更新業務、管理者ユーザーによる全社モニタリング・マスター管理業務の振る舞いを完全維持し、フレームワーク移行による業務停止や操作感の悪化を生じさせない。
- **モダンなポータル体験とパフォーマンス**: Next.js App Router の高速なクライアントサイドナビゲーションと最適化されたコード分割により、軽快な操作レスポンスを提供する。
- **本番リリース相当の信頼性**: 画面コンテナおよび別コンテナ Mock API 接続により、実運用に近いコンテナインフラ環境での動作を保証する。

### 1.3 開発・技術検証目的

本リポジトリ（`react-practice-notes`）は、React、TypeScript、Next.js (App Router) を用いた業務フロントエンド開発の実践と、ウォーターフォール開発工程（RD → ED → ID → C・UT → IT → PT）の進行を学習・実証するためのものです。
実バックエンドは作成せず、REST API の仕様は `docs/ed/api/openapi.yaml` を唯一の正本（SSOT）として定義します。モック環境として、開発・単体テスト（UT）・結合テスト（IT）では MSW を継続利用し、リリース相当の接続確認や総合テスト（PT）では別コンテナ Mock API サーバーを `/api` 経路で利用する 2 層の検証基盤を構築します。

## 2. 対象利用者とロール定義

業務上の職務分掌・責務分離（SoD: Separation of Duties）に基づき、利用者を「一般ユーザー」と「管理者ユーザー」の 2 つのロールに明確に分離します。

### 2.1 利用者（アクター）の定義

| ロール / アクター                      | 定義と位置づけ                                                                       | 主な業務責務と操作範囲                                                                                                                                                                                                                                                                                                                                                      |
| :------------------------------------- | :----------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **一般ユーザー**<br>（業務担当者）     | 特定のプロジェクトに1つ以上所属し、日々の問い合わせ起票や対応業務を行う担当者        | ・ログイン認証、所属プロジェクトの切り替え（複数所属時）<br>・自プロジェクトのチケット件数サマリーおよび担当案件の確認（ダッシュボード）<br>・自プロジェクトの問い合わせ一覧閲覧、検索・絞り込み<br>・自プロジェクトの問い合わせ新規起票<br>・チケットのステータス/担当者更新、コメント追加<br>・※ システム管理画面へのアクセスは不可（403 ガード）                         |
| **管理者ユーザー**<br>（システム管理） | 全社の基盤管理およびセキュリティ・運用監査を担うシステム管理者（プロジェクト非所属） | ・ログイン認証、全社システムのモニタリング<br>・全プロジェクト横断の問い合わせ件数・稼働サマリー・滞留アラートの確認（ダッシュボード）<br>・全社横断の問い合わせ一覧の閲覧、プロジェクト絞り込み検索<br>・チケット詳細の**閲覧専用（Read-only）**確認<br>・プロジェクトおよびユーザーの追加・削除、所属紐づけ管理<br>・※ 新規起票および更新・コメント操作は不可（SoD 制限） |

### 2.2 職務分掌と責務分離（SoD: Separation of Duties）原則

システム監査および業務統制の観点から、以下の責務分離ルールを徹底します。

1. **業務データ改変とシステム管理の分離**:
   - 管理者ユーザーは、プロジェクトマスターやユーザーアカウントの管理、全社の運用状況監査を行う権限を持ちますが、**問い合わせデータの作成・更新・コメント投稿を行うことはできません**。これにより、管理特権による業務データの捏造や改変を防止します。
2. **プロジェクトデータへのアクセス制限**:
   - 一般ユーザーは、自らの所属するプロジェクトのデータのみを起票・閲覧・更新できます。他プロジェクトのチケット閲覧・更新や、全社マスター（プロジェクト/ユーザー管理）の改変はできません。

### 2.3 ロール責務と画面アクセス制御マトリクス

各画面（SCR-AUTH〜SCR-04 および共通 404）に対するロールごとのアクセス権限と操作権限を以下のように定めます（[docs/rd/step3.md#21-ルーティングとコンポーネント移行方針](../rd/step3.md#21-ルーティングとコンポーネント移行方針) に準拠）。Next.js App Router による URL ルートパスを併記します。

| 画面 ID      | 画面名                         | Next.js ルートパス     | 一般ユーザー（業務運用）                                    | 管理者ユーザー（システム管理・監査）                      | 未認証ユーザー                                 |
| :----------- | :----------------------------- | :--------------------- | :---------------------------------------------------------- | :-------------------------------------------------------- | :--------------------------------------------- |
| **SCR-AUTH** | ログイン画面                   | `/login`               | ログイン可能（所属プロジェクト権限確立）                    | ログイン可能（管理者権限確立）                            | ログイン画面表示                               |
| **SCR-00**   | ダッシュボード画面             | `/dashboard`           | **自プロジェクト**のサマリー・担当案件リンク表示            | **全プロジェクト横断**の集計サマリー・滞留アラート表示    | ログインへ遷移                                 |
| **SCR-01**   | 問い合わせ一覧画面             | `/tickets`             | **自プロジェクト**のチケットのみ表示                        | **全プロジェクト**のチケットを閲覧（プロジェクト絞込可）  | ログインへ遷移                                 |
| **SCR-02**   | 問い合わせ詳細画面             | `/tickets/[id]`        | 閲覧 ＋ **操作可能**（ステータス/担当者更新、コメント追加） | **閲覧専用（Read-only）**（更新・コメントフォーム非表示） | ログインへ遷移                                 |
| **SCR-03**   | 問い合わせ新規起票画面         | `/tickets/new`         | **利用可能**（自プロジェクトのチケットを登録）              | **利用不可（アクセス不可 / 403 エラー）**                 | ログインへ遷移                                 |
| **SCR-04**   | ユーザー・プロジェクト管理画面 | `/admin/management` ※1 | **利用不可（アクセス不可 / 403 エラー）**                   | **利用可能**（プロジェクト/ユーザー/所属紐づけの管理）    | ログインへ遷移                                 |
| **共通**     | 未定義パス（404）              | （未定義の全パス）     | 404 Not Found 画面表示（ポータル復帰導線）                  | 404 Not Found 画面表示（ポータル復帰導線）                | 404 Not Found 画面表示（ログインへの復帰導線） |

※1: `/admin` へのアクセスは `/admin/management` へリダイレクトされます。

## 3. 対象範囲

### 3.1 含む範囲（Step 3 対象機能）

合意済みの要件定義（`docs/rd/step3.md`）に基づき、以下の機能を対象範囲とします。

1. **Next.js (App Router) 移行基盤**
   - **ファイルベースルーティング**: `src/app/**/page.tsx`、`layout.tsx`、`not-found.tsx` によるルート定義（`/login`, `/dashboard`, `/tickets`, `/tickets/new`, `/tickets/[id]`, `/admin/management`）。
   - **Client Components 中心構成**: 既存の画面・UI コンポーネント（`src/features/`、`src/shared/`）およびカスタムフックは `"use client"` を基本とし、既存の React 状態管理や MSW との親和性を維持。
   - **ナビゲーション API 刷新**: 画面遷移・URL クエリ操作を `next/navigation`（`useRouter`, `usePathname`, `useSearchParams`）へ置き換え。
   - **グローバル CSS の一元管理**: Next.js の Root Layout（`src/app/layout.tsx`）と Storybook（`.storybook/preview.ts`）で読み込むグローバル CSS を同一ファイルに統一し、実画面と Storybook VRT の描画スタイル完全一致を保証。
2. **コンテナイメージ提供および別コンテナ Mock API 接続**
   - **画面コンテナイメージ**: Next.js アプリケーションを本番ビルド・パッケージ化した Docker コンテナイメージの提供。
   - **Mock API コンテナ**: OpenAPI 契約（`docs/ed/api/openapi.yaml`）と既存モックデータ（`src/mocks/db/`）を活用する独立した API サーバーコンテナの提供。
   - **`/api` 接続経路**: 画面コンテナから Mock API コンテナへ、本番想定の `/api` 経路（Rewrites またはリバースプロキシ）を通じて透過的に接続。
3. **認証・セッション管理基盤（振る舞い維持）**
   - **ログイン画面（SCR-AUTH）**: ユーザー名・パスワードによる認証。入力されたユーザー名に応じてロール（一般 / 管理者）および所属プロジェクトを判定。
   - **セッション保持 & ログアウト**: ログイン状態を保持し、ブラウザリロード時もセッションを維持。共通ヘッダーまたはサイドバーにユーザー情報とログアウトボタンを常設。
   - **未認証ガード（Auth Guard）**: 未ログイン状態での保護ルートアクセスを検知し、ログイン画面へリダイレクト（`?redirect=` クエリによるログイン後元画面復帰）。
4. **共通レイアウト & 開閉式サイドバーナビゲーション（振る舞い維持）**
   - **開閉式サイドバー**: 右上トグルボタン（`←` / `→`）により展開（幅約240px）と折りたたみ（幅約60px、アイコン表示）を切り替え。開閉状態を `localStorage` に保持。モバイル幅（375px）ではドロワー表示。
   - **ロール別 3 枠メニュー**:
     - 一般ユーザー: 📊 ダッシュボード / 📋 問い合わせ一覧 / ➕ 新規起票
     - 管理者ユーザー: 📊 ダッシュボード / 📋 問い合わせ一覧 / ⚙️ ユーザー・プロジェクト管理
   - **画面離脱防止（Dirty State ガード）**: 新規起票画面やコメント入力中、または所属紐づけ編集中の未保存変更がある状態で別画面へ遷移しようとした場合、確認ダイアログを表示して破棄を確認。
5. **ダッシュボード機能（SCR-00、振る舞い維持）**
   - ロール別表示分岐:
     - 一般ユーザー: 所属プロジェクトのステータス別（未対応/対応中/完了）チケット件数サマリー、自分宛ての担当チケット一覧（クイックリンク）。
     - 管理者ユーザー: 全プロジェクト横断の総チケット件数・ステータス集計、プロジェクト別チケット稼働サマリー、未割り当て・滞留案件アラート。
6. **問い合わせ一覧機能（SCR-01、振る舞い維持）**
   - チケットエンティティへの「所属プロジェクト（`projectId`, `projectName`）」追加とテーブル列表示。
   - 一般ユーザー: 自プロジェクトのチケットのみ表示（複数プロジェクト所属時は、自所属プロジェクト間での絞り込みフィルターを利用可能）。
   - 管理者ユーザー: 全プロジェクト横断で全チケットを表示、プロジェクト絞り込みフィルターを追加。
   - 既存機能の維持（ステータス・担当者絞り込み、キーワード検索、起票日フィルター、ソート、ページネーション）。
7. **問い合わせ詳細・コメント閲覧・更新機能（SCR-02、振る舞い維持）**
   - 所属プロジェクトの表示。
   - 一般ユーザー: 閲覧 ＋ ステータス更新 ＋ 担当者変更 ＋ コメント追加。
   - 管理者ユーザー: **閲覧専用（Read-only）**。更新フォームおよびコメント入力フォームは非表示（または非活性）。
8. **問い合わせ新規起票機能（SCR-03、振る舞い維持）**
   - 一般ユーザー専用機能（管理者はアクセス不可 / 403 エラー）。
   - タイトル、問い合わせ本文、所属プロジェクト（所属が1つの場合は自動設定、複数所属時は選択）、担当者（任意）の入力。
   - 起票者（`created_by`）はログイン中ユーザーを自動設定。
   - 登録完了後、作成されたチケットの詳細画面（`/tickets/[id]`）または一覧画面へ自動遷移。
9. **ユーザー・プロジェクト管理機能（SCR-04、振る舞い維持）**
   - 管理者専用機能（一般ユーザーはアクセス不可 / 403 エラー）。
   - プロジェクト管理: 一覧閲覧、新規プロジェクト追加、プロジェクト削除。
   - ユーザー管理: 一覧閲覧、新規ユーザー追加、ユーザー削除。
   - 所属紐づけ管理: ユーザーごとの所属プロジェクト設定・更新。
10. **共通画面状態・フィードバック・エラーハンドリング（振る舞い維持・拡充）**
    - 読み込み中（ローディングスピナー等）、空状態（0件ガイダンス）、入力エラー、API エラー表示（再試行ボタン）。
    - 認可・アクセスエラー表示（403 Forbidden、401 Unauthorized）。
    - チケット未存在時の画面内 404 エラー表示（`/tickets/[id]`）と、未定義パスアクセス時の Next.js 共通 404 フォールバック（`not-found.tsx`）の切り分け。
11. **モック API 連携（OpenAPI 契約 SSOT）**
    - `docs/ed/api/openapi.yaml` を唯一の正本（SSOT）とし、開発・UT・IT では MSW モック、リリース相当・PT では別コンテナ Mock API サーバーを利用。
    - MSW ストアおよび Mock API データベースにおけるユーザー・プロジェクト・チケットのリレーショナルデータ整合性の維持。
12. **UT / IT / PT テスト・品質保証体系の刷新**
    - **UT**: 全 `.tsx` への `.stories.tsx` 必須作成、`.test.tsx` 補完、親子分離（親の試験で子のバリエーションを兼ねない）、C0/C1 カバレッジ 100% 網羅原則、VRT（Playwright VRT）の UT（Storybook）への一本化。
    - **IT**: Playwright Test（実ブラウザ駆動）への移行、全ケースでのトレース常時記録（`trace: "on"`）、HTML/JSON レポート常時出力、Markdown 実行結果サマリー表の Git コミット（IT での VRT は実施しない）。
    - **PT**: Next.js コンテナ ＋ Mock API コンテナ環境での実ブラウザ手動受入、初期ロード JavaScript バンドルサイズ 100.0 kB 未満の達成検証、Lighthouse、Total-DRE（総合欠陥除去率）の品質分析。

### 3.2 対象外（本スコープに含めない機能・将来課題）

以下の機能・要求は、Step 2 から継続して Step 3 でも対象外とし、将来の実バックエンド開発や運用拡張時に検討します（[docs/rd/step3.md#23-対象外とする機能将来課題として維持](../rd/step3.md#23-対象外とする機能将来課題として維持) に準拠）。

- **管理者操作（プロジェクト削除、ロール変更）の監査ログ永続化**: Step 2 PT 申し送り事項（No.3）。Step 3 では実バックエンド・永続化層の開発を行わないため、引き続き対象外とします。
- **チケットの物理削除・コメントの編集および削除**: 業務データ保全およびスコープ管理のため対象外を維持します。
- **多要素認証（MFA）およびブルートフォース攻撃対策**: 認証セキュリティの高度化は将来課題として維持します。
- **ダッシュボードの未完了判定しきい値カスタマイズ**: 固定しきい値仕様を維持します。
- **実バックエンドサーバーの実装および実データベース接続**: OpenAPI 契約に準拠したモック環境（MSW および Mock API コンテナ）で完結します。
- **高度なセキュリティ・暗号化**: パスワードのソルト/ハッシュ化、JWT 署名検証、HTTPS 暗号化通信などは行わず、モック環境でのロール分離の再現に限定します。
- **添付ファイル管理**: 画像やドキュメントのアップロード・ダウンロードは対象外とします。
- **外部通知連携**: メール通知や Slack/Teams 等のチャット連携は対象外とします。
- **無限スクロール**: ページ送りのページネーションを採用し、無限スクロールは対象外とします。

## 4. 業務上・技術上の用語と前提

### 4.1 用語の定義

| 用語                                  | 定義                                                                                                                                                                            |
| :------------------------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **問い合わせ / チケット**             | 社内ユーザーから寄せられた要望・質問・トラブル報告の1案件を表す業務エンティティ。本ドキュメントおよびシステム内では同義として扱う。                                             |
| **プロジェクト**                      | 問い合わせやユーザーが属する業務・開発の単位（例: `ECサイト刷新`, `社内基盤刷新`）。チケットはいずれか1つのプロジェクトに必ず紐づく。                                           |
| **一般ユーザー**                      | 1つ以上のプロジェクトに所属し、チケットの起票・対応・更新を行う業務アクター。                                                                                                   |
| **管理者ユーザー**                    | システム基盤の管理（ユーザー/プロジェクト管理）および全社の運用状況監査を担うアクター。特定のプロジェクトには所属しない。                                                       |
| **ロールベースアクセス制御 (RBAC)**   | 利用者のロール（一般 / 管理者）に基づいて、アクセス可能な画面や実行可能な操作を制御する仕組み。                                                                                 |
| **職務分掌 / 責務分離 (SoD)**         | 不正や誤操作を防止するため、システム管理者と業務運用者の権限を分離する原則（管理者は業務データを改変できず、一般ユーザーはマスター設定を改変できない）。                        |
| **Next.js (App Router)**              | React ベースのモダン Web フレームワーク。ディレクトリ構造に基づくファイルベースルーティング（`page.tsx`, `layout.tsx`, `not-found.tsx` 等）およびルート別コード分割を提供する。 |
| **Client Component (`"use client"`)** | クライアント（ブラウザ）側でレンダリングおよび状態管理を行うコンポーネント。既存の React 状態管理やカスタムフック、MSW との親和性を維持するために採用する。                     |
| **Next.js 画面コンテナ**              | Next.js アプリケーションを本番ビルド・パッケージ化した Docker コンテナイメージ。                                                                                                |
| **Mock API コンテナ**                 | OpenAPI 契約（`docs/ed/api/openapi.yaml`）およびモックデータ（`src/mocks/db/`）を活用し、独立して稼働する軽量 API サーバーコンテナ。                                            |
| **`/api` 接続経路**                   | 画面コンテナから Mock API コンテナへ通信する際の本番想定 URL パス経路。Next.js Rewrites またはリバースプロキシ等によりプロキシ接続される。                                      |
| **セッション**                        | ログイン成功後に保持されるユーザーの認証状態。ブラウザリロード後も `localStorage` 等を通じて維持される。                                                                        |
| **未認証ガード (Auth Guard)**         | 未ログインユーザーが保護された画面へアクセスした際に検知し、ログイン画面へ強制リダイレクトする制御（`?redirect=` で元画面 URL を保持）。                                        |
| **画面離脱防止 (Dirty State ガード)** | フォーム入力中（未保存変更がある状態）に、サイドバーナビゲーションやブラウザ戻る等で画面を離脱しようとした際、変更破棄を確認する制御。                                          |
| **開閉式サイドバー**                  | 画面左側に常設され、アイコン表示（折りたたみ）と名称表示（展開）をトグル切り替えできる共通ナビゲーション。                                                                      |
| **ステータス**                        | 問い合わせの対応進捗区分（「未対応」「対応中」「完了」の3値）。                                                                                                                 |
| **担当者**                            | 問い合わせの調査・対応を担当する社内メンバー。未割り当て（未設定 / null）を許容する。                                                                                           |
| **起票者**                            | 問い合わせを最初に登録したユーザー。新規起票時にログイン中ユーザーが自動設定される。                                                                                            |
| **コメント**                          | 問い合わせに対して追加される対応履歴、進捗メモ、連絡事項の時系列記録。                                                                                                          |
| **トレース常時記録 (`trace: "on"`)**  | IT（Playwright）実行時に DOM スナップショット、画面遷移、ネットワーク通信、Console ログを全テストケースで常時記録する機能。                                                     |

### 4.2 業務上・技術上の前提

1. **画面環境・実行環境**:
   - 社内 PC のモダンブラウザ（デスクトップ環境 1280px 以上）を基本とし、モバイル幅（375px）ではサイドバーがドロワー表示となるレスポンシブ構成を前提とします。
   - 本番相当環境（PT・接続検証）では、Docker コンテナ（Next.js 画面コンテナ ＋ Mock API コンテナ）上で動作します。
2. **データの永続化とリレーショナル整合性**:
   - 実 DB を持たないため、MSW ストアおよび Mock API コンテナ内でユーザー・プロジェクト・チケットの相互参照の整合性を保持します。ブラウザリロード後もセッションおよび操作結果が保持される設計とします。
3. **API 仕様の正本 (SSOT)**:
   - REST API のパス、パラメータ、データ構造は `docs/ed/api/openapi.yaml` を唯一の正本（SSOT）とし、推測による API 仕様の先行確定を行いません。
4. **担当者の識別とプロジェクト**:
   - 一般ユーザーはプロジェクトに所属しており、新規起票や担当者割り当てにおいては該当プロジェクトに所属するメンバーが候補となります。
5. **認証情報のモック仕様**:
   - モック環境のため平文ユーザー名・パスワードによる簡易認証とし、ユーザー名に応じた固定ロール（例: `admin` → 管理者、`user1`/`user2` → 一般）を割り当てます。
6. **モック提供の 2 層構成**:
   - 開発・単体テスト（UT）・結合テスト（IT）では MSW を継続利用し、リリース相当の接続確認および総合テスト（PT）では別コンテナ Mock API サーバーへ `/api` 経路で接続します。
7. **フロントエンド基盤**:
   - Next.js App Router、Client Component（`"use client"`）、`next/navigation`（`useRouter`, `usePathname`, `useSearchParams`）を使用します。
   - Next.js Root Layout と Storybook preview で読み込むグローバル CSS を同一ファイルに一元化します。

## 6. 確認事項・未確定事項

### 6.1 合意済み業務・技術ルール

1. **ロールと責務分離（SoD）**:
   - 一般ユーザー（業務運用）と管理者ユーザー（基盤管理・全社監査）の 2 ロール体制とする。
   - 管理者は問い合わせの新規起票、ステータス/担当者更新、コメント追加を行えない（Read-only 閲覧専用）。
   - 一般ユーザーはプロジェクト/ユーザー管理画面へアクセスできない（403 ガード）。
2. **プロジェクト紐づけとデータスコープ**:
   - チケットは必ず 1 つのプロジェクトに紐づく。
   - 一般ユーザーは自プロジェクトのチケットのみ表示・起票・更新可能。管理者は全プロジェクト横断で閲覧可能。
3. **ステータス値の種類と遷移規則**:
   - ステータスは「未対応」「対応中」「完了」の 3 値（`docs/ed/api/openapi.yaml`）。
   - ステータス間の遷移順序に機械的制約は設けない。
4. **担当者の未割り当て**:
   - チケット起票直後など、担当者が「未割り当て（未設定 / null）」の状態を許容する。
5. **サイドバー構成**:
   - 開閉トグル（幅 240px 展開 / 幅 60px 折りたたみ）をサポートし、状態は `localStorage` に保持する。
   - ロールごとに「3つの枠」で整列したナビゲーションメニューを提供する。
6. **画面離脱防止（Dirty State ガード）**:
   - 新規起票画面、詳細画面のコメント入力中、および管理画面の所属紐づけ編集中に未保存の変更がある状態で別画面へ遷移しようとした場合、確認ダイアログを表示して誤操作を防止する。
7. **モック認証の仕様**:
   - 簡易ユーザー名認証とし、入力されたユーザー名に応じてロール（一般 / 管理者）および所属プロジェクトを判定・返却する。
8. **Next.js App Router 構成と Client Components 方針**:
   - ファイルベースルーティング（`src/app/**/page.tsx` 等）を採用し、既存の画面・UI コンポーネントおよびカスタムフックは `"use client"` を基本として既存 React 状態管理や MSW との親和性を担保する。
   - 画面遷移・URL パラメータ制御は `next/navigation` を利用する。
9. **モック提供の 2 層構成**:
   - 開発・単体テスト（UT）・結合テスト（IT）では MSW を継続利用し、リリース相当の接続確認や総合テスト（PT）では別コンテナ Mock API サーバーへ `/api` 経路で接続する。
10. **グローバル CSS 一元管理方針**:
    - Next.js Root Layout と Storybook preview で読み込むグローバル CSS を同一ファイルに統一し、VRT と実画面の描画スタイル完全一致を保証する。
11. **UT / IT / PT 品質保証体系**:
    - UT: 全 `.tsx` への `.stories.tsx` 必須作成、`.test.tsx` 補完、親子分離、C0/C1 100% 網羅、VRT 一本化。
    - IT: Playwright Test（実ブラウザ駆動）、全ケース `trace: "on"` 常時記録、HTML/JSON レポート常時出力、Markdown 実行結果サマリー表の Git コミット（IT での VRT は実施しない）。
    - PT: Next.js コンテナ ＋ Mock API コンテナ環境での手動業務受入（SYS-AC-01〜SYS-AC-16）、非機能・品質特性検証（SYS-AC-17: 画面固有チャンク 100.0 kB 未満・ルート初期ロード JavaScript バンドルサイズ 130.0 kB 未満、Lighthouse Accessibility/Best Practices 各 90 点以上、キーボード操作性、WCAG 2.1 AA コントラスト比、1280px / 375px レスポンシブ表示と証跡取得）、Total-DRE 品質分析。
