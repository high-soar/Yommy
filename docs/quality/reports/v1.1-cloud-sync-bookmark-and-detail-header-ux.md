### 3.2 主要傾向の分析

1. **原因 `D`（38.6%）は仕様書・トレーサビリティ・同期契約の多拠点分散が主因**:
   - 支援成果物 17 件のうち多くは、複数 Issue が並行して同一画面（`SCR-02` `novel-detail.md` と `requirements.md` の `AC-ND-27` 衝突 `No. 402`）や複数レイヤー（`issue-342` / `reader-view.md` / `bookshelf.md` / `architecture.md` / `webview-import.md`）へ変更を加えた際の **正本・双方向 ID・ディレクトリ図・PR/Issue 本文の同期漏れ**（`No. 399–403, 412–414, 418, 419, 421, 432, 434, 435, 441`）でした。
   - 製品コードの `D` 5 件（`No. 389, 406, 424, 426, 428`）は、要件の画面適用範囲や仕様境界の詰めの甘さに起因します（設定画面フックの自動 Pull 購読漏れ `No. 428`、他端末新着話の目次補完・範囲外しおり保護漏れ `No. 424`、競合ダイアログ背面 `inert`・フォーカストラップ設計漏れ `No. 426`、競合解決完了前のモーダル即時消滅 `No. 406`、サイレント更新と通常ローディングの区別不足 `No. 389`）。
2. **原因 `L`（38.6%）は支援成果物（テスト規約・台帳・IT カバレッジ・ドキュメント整合）に集中（製品 `L` は僅か 2 件）**:
   - 製品コードの `L` は 2 件（`No. 417`: 3 点メニュー循環フォーカスと非 null アサーション排除、`No. 436`: サイレント更新失敗時の `!silent` ガード）に留まり、残る 20 件は **親子分離テスト規律違反（`No. 392, 393, 396, 411`）、Story / VRT 作成・更新漏れ（`No. 391, 425`）、IT シナリオ経路不足（`No. 409, 410, 431`）、台帳・PR 要約・レポート・ガイドライン誤記（`No. 398, 415, 420, 433, 437, 439, 440, 443, 444, 445`）、および `vi.spyOn` 復元（`No. 442`）** でした。設計 PR・MK PR で親子分離や ID 管理を徹底したつもりでも、急ぎ修正やドキュメント執筆時に識別子・シンボル名・件数転記のケアレスミスが再発する点が課題です。
3. **原因 `S`（10.5%）および `A`（8.8%）が製品コード品質の最重要ボトルネック**:
   - 製品コード 14 件のうち **`S` 4 件（28.6%: `No. 394, 423, 429, 438`）＋ `A` 3 件（21.4%: `No. 407, 422, 427`）＝ 計 7 件（製品不備のちょうど 50.0%）** が React Hook / ServiceProvider / 非同期 `await` / デバウンスタイマーのライフサイクル境界に集中しました。

## 6. プロセス・ガイドライン・スキル改善アクション（Kaizen 5 施策）

`v1.1` で検出された製品不備（`S`/`A`/`D`/`L`）およびテスト・台帳運用の再発を恒久防止するため、[docs/guidelines/testing.md](../../guidelines/testing.md)（`§3.9`）および [.github/skills/c-ut-workflow/SKILL.md](../../../.github/skills/c-ut-workflow/SKILL.md) へ以下の **5 施策** を反映しました。

1. **モーダル競合解決の非同期状態維持・タイマー解除・未操作離脱保護・背面 `inert` 規律（`No. 406, 422, 423, 426`: `R1-01, R1-17, R1-18, R1-21` 再発防止）**:
   - 競合解決ハンドラ（`resolveBookmarkConflict` 等）は `async Promise<boolean>` として保存・解決成功後にのみダイアログ状態（`bookmarkConflict`）を閉じ、失敗時はモーダルを維持して再操作・再試行を許容すること。
   - 競合状態中（`bookmarkConflict != null`）およびデバウンスタイマー残存時は `clearTimeout` と自動保存・アンマウント保存の双方を遮断し、未読本文の取得失敗時や既読再閲覧のみでダーティフラグ（`hasPendingBookmarkRef`）を立てないこと。
   - 破壊的確認ダイアログや競合ダイアログでは初期フォーカス移動・`Tab`/`Shift+Tab` トラップに加え、背面ツリーへの `inert` 属性付与と Android OS 戻るキー／背景タップ抑止を標準実装すること。
2. **バックグラウンド自動 Pull 購読の全画面網羅・サイレント再読込・排他処理遅延調停・差分目次補完（`No. 389, 424, 427, 428, 436`: `R1-19, R1-22, R1-23, R1-31` 再発防止）**:
   - 同期エンジン完了通知（`subscribePullCompleted`）は、本棚・詳細・リーダーだけでなく設定画面（`SCR-05`）等の同期状態表示画面にも漏れなく接続し、バックグラウンド再読込（`{ silent: true }`）時はフルスクリーンローディングやエラー画面遷移（`!silent` ガード）を抑止すること。
   - 一括キャッシュ・削除・手動更新等の排他処理実行中に届いた自動 Pull 完了通知は即座に破棄せず、`pendingSilentReloadRef` 等で予約して排他解放直後に遅延再実行すること。
   - 他端末 Pull/Push マージ時は、リモートしおり話数がローカル目次数を超える場合に範囲外しおり破壊を防ぎつつ、作品情報・不足目次メタを自動補完する設計を徹底すること。
3. **DI Provider 初期フォールバック参照安定化と非同期 `await` 境界アンマウント保護・派生 State 原則（`No. 407, 429, 438`: `R1-02, R1-24` 再発防止）**:
   - React Context Provider（`ServiceProvider` 等）の非ネイティブフォールバックオブジェクト・インスタンス生成は、再レンダーごとに新規参照を生成しないようモジュール定数化または `useMemo` で参照安定性を保証し、下流 `useEffect` タイマーの意図しないリセットを防止すること。
   - すべての非同期操作（`startBatchCache` / `confirmClearCache` / `toggleFavorite` 等）の `await` 直後には `isMountedRef.current` および Abort 状態を必ず再検証し、アンマウント後のステート更新や中断後 DB 書き込みを遮断すること。
4. **VRT 全件スナップショット更新（`--update-snapshots=all`）＆ 許容閾値 `0.001`・IT 仮想時計（`window.Date` `Proxy`）統一規律（`No. 395, 408, 425, 430`: `R1-03, R1-20, R1-25` 再発防止）**:
   - UI や Storybook 変更時は `npm run test:vrt:update`（内部で `--update-snapshots=all` 実行）により 1280px/375px 全件基準画像を更新し、`maxDiffPixelRatio: 0.001` の厳格閾値を維持すること。
   - Playwright IT では固定待機（`waitForTimeout`）および固定未来日・実時計依存を禁止し、時刻経過を伴うテストは `window.Date` `Proxy` による決定論的仮想時計ユーティリティ＋`expect.poll` で安定化すること。
5. **単体テストの `vi.spyOn` 確実復元（`afterEach` / `try-finally`）と Step 2 設計更新 PR レビュー指摘の台帳即時記録（`No. 397, 415, 416, 442`: `R1-10, R1-11` 再発防止）**:
   - テスト内で生成した `vi.spyOn` スパイはアサーション失敗時も必ず復元されるよう `afterEach(() => vi.restoreAllMocks())` または `try { ... } finally { spy.mockRestore(); }` で管理すること。
   - Step 3 MK PR だけでなく **Step 2 設計更新 PR** における `pr-reviewer` 指摘事項（`D` を含む全指摘）も、是正コミットと同一 PR 内で `docs/quality/bug-and-handover-log.md` へ即時記録すること。
