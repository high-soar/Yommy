## 1. 背景と目的

ソフトウェア開発の品質分析において、単体テスト（UT）フェーズでの品質評価指標の一つとして「バグ密度（件/KLoC、件/ケース数）」を算出・報告します。

TDD（テスト駆動開発）では「Red（テスト失敗確認） → Green（最小限の実装） → Refactor（改善）」を小刻みに繰り返します。AI 駆動開発では、実装中だけでなく、テスト作成、静的・自動検証、AI による PR レビューなど複数の作業工程で不備が発見されます。Green 工程だけを対象にすると、他の工程で確認された不備を取りこぼします。

そこで本実験では、**C・UT 工程で AI が作業中に確認した不備を、検出工程・検出手段・成果物区分ごとに記録し、UT 品質分析（バグ密度および原因分類）に用いる手法**を検証します。計測するのは AI が発見した不備であり、AI がその不備を作り込んだと一律にみなすものではありません。不備の所在・由来と検出工程を分けて記録します。Green は複数ある検出工程の一つとして扱います。

## 2. バグ判定基準と記録ルール

### 2.1 バグとして記録する対象

- **対象範囲**: Step 2 の C・UT 作業で、AI が TDD（Red / Green / Refactor）、自動検証、AI によるコードレビューなどを通じて確認した、仕様・承認済み設計または期待される動作に反する一意の不備を記録します。
- **確認条件**: 再現可能な誤動作、契約違反、または成果物の誤りとして確認できたものを対象とします。レビュー上の懸念や推測だけでは記録せず、仕様・コード・テスト等の根拠を確認してから記録します。
- **成果物区分**:
  - **製品コード**: 実行時のアプリケーションコード。KLoC 密度の分母と対応させるため、テスト、Storybook、`src/mocks/**` は除外します。
  - **テスト・モック等支援成果物**: 単体テスト、MSW ハンドラー、Storybook / VRT、テスト・ビルド設定など。確認済み不備の件数としては記録しますが、製品コードのバグ密度の分子には加えず、別集計します。
- **検出工程・手段**: `TDD Red`、`Green`、`Refactor`、`自動検証`（テスト・型チェック等）、`AIレビュー` などを記録します。Green は唯一の対象ではありません。
- **不備の由来**: 不備が以前から存在したか、今回のタスク成果物に存在したかを根拠がある範囲で記録します。「AI が発見したこと」と「AI が作り込んだこと」は区別し、由来を確認できない場合は推測しません。
- **原因分類の例**:
  - **ロジック誤り**: 条件分岐の真偽判定逆転、ループ条件ミス、計算式の誤り。
  - **状態遷移誤り**: React state の更新漏れ、Context 購読の不整合、初期値誤り、不要な再レンダリングによる状態リセット。
  - **設計・仕様誤認**: 内部設計書（ID）や OpenAPI 契約の見落とし・解釈ミス、Props や戻り値型の不整合。
  - **境界値・エッジケース未考慮**: 空文字、空配列、`null` / `undefined`、最大最小値の考慮漏れ。
  - **非同期制御不備**: Promise のエラーハンドリング漏れ、`AbortController` のシグナル未連携、Race Condition 防止漏れ。

### 2.2 バグとして記録しない対象（除外対象）

以下は確認済み不備としてカウントしません。

1. **通常の Red step**:
   - 未実装機能をテストが仕様どおり検出して意図的に失敗する状態は記録しません。ただし、Red テストを通じて既存成果物が承認済み仕様に反することを確認した場合は、Red の失敗そのものではなく、既存の不備を一件として記録します。
2. **不備と確認できない指摘・一時的な失敗**:
   - 根拠のないレビューコメント、環境・依存関係の障害、再現しない不安定なテストなどは記録しません。テストの失敗だけで製品コードの不備と判断せず、失敗原因を特定します。
3. **品質上の不備ではない修正**:
   - 振る舞いや契約に影響しない整形・命名・文体の修正、編集中の一時的な構文エラーや軽微なタイポは記録しません。型チェック等で検出された場合も、成果物に実在する不備かを確認して区分します。
4. **Refactor step における脆いテストの破損**:
   - プロダクションコードの振る舞いを変えていないにもかかわらず、内部実装詳細（プライベートプロパティや非公開ステート）に依存していたためにテストが失敗した場合（Brittle Test の解消としてテスト側をリファクタするケース）。
   - テストが実際に仕様を誤って表現していると確認できた場合は、この除外にせず、テスト・支援成果物の不備として記録します。Refactor 時にプロダクションコードを誤って変更し、振る舞いを壊した場合も記録対象です。

### 2.3 重複記録の防止ルール

開発リズムを維持し、かつバグ件数の水増し（過大評価）を防ぐため、以下の重複除外基準を厳格に適用します。

1. **工程・Issue をまたぐ同一不備**:
   - 同じ根本原因の不備が Red、Green、自動検証、AIレビュー等で再度検出・確認されても一件だけ記録します。最初に確認した工程・手段と検出 Issue に記録し、後続のテスト失敗やレビューは同じ記録の根拠に加えます。
2. **同一の修正トライアル・連鎖的失敗**:
   - 修正後も同じ原因で同一または関連するテストが失敗した場合、または同一テストケース・同一処理ブロックの連鎖的失敗は、根本原因が同じなら一件に集約します。
3. **別原因・別責務の不備**:
   - 同一成果物内でも独立した原因・機能・分岐に起因する不備は別件として記録します。すでに AI レビューで見つけた不備を確認するための回帰テストは、追加の不備として数えません。

## 3. バグ記録フォーマット

記録の均質性と集計の容易性を担保するため、以下の 11 項目を記録するテーブル形式を採用します。

### 3.1 記録テーブル項目

| 項目名                                   | 内容・記載例                                                          |
| :--------------------------------------- | :-------------------------------------------------------------------- |
| **No.**                                  | 各検出 Issue 内での通し番号（1, 2, ...）                              |
| **検出日時**                             | 不備を最初に確認した日時（`YYYY-MM-DD HH:mm`、JST）                   |
| **検出 Issue**                           | 不備を検出した作業 Issue（発生元の Issue と異なる場合は由来欄に記載） |
| **検出工程・手段**                       | `TDD Red`、`Green`、`Refactor`、`自動検証`、`AIレビュー` 等           |
| **成果物区分**                           | `製品コード` または `テスト・モック等支援成果物`                      |
| **対象ファイル / 関数 / コンポーネント** | 不備が確認されたファイルパスおよびシンボル名                          |
| **現象・根拠**                           | 再現した動作、失敗したテスト、レビュー指摘等の証拠                    |
| **原因分類**                             | 下記 5 分類コード（`L` / `S` / `D` / `B` / `A`）                      |
| **不備の具体的原因・由来**               | 根本原因と既存・今回成果物等の由来（確認できる範囲で記載）            |
| **是正内容**                             | 不備を解消した変更と、可能な場合は修正コミット                        |
| **重複判定**                             | `新規` または同一不備の再検出（件数には再加算しないことを明記）       |

### 3.2 不備の原因分類コード（5 分類）

| コード | 分類名                       | 主な事象例                                                                  |
| :----: | :--------------------------- | :-------------------------------------------------------------------------- |
| **L**  | **Logic（ロジック誤り）**    | 条件分岐ミス、ループ処理誤り、計算式の誤り、真偽値の反転                    |
| **S**  | **State（状態遷移誤り）**    | React state 更新漏れ、Context 値の不整合、ライフサイクル・初期化タイミング  |
| **D**  | **Design（設計・仕様誤認）** | ID/ED 設計書や OpenAPI 契約の見落とし、型定義・引数の不一致                 |
| **B**  | **Boundary（境界値未考慮）** | `null` / `undefined` の考慮漏れ、空配列・空文字、最大値・最小値の扱い漏れ   |
| **A**  | **Async（非同期制御不備）**  | Promise ハンドリング漏れ、`AbortController` 未連携、Race Condition 防止漏れ |

| 検討案                                                              | 概要                                                        | 評価・メリデメ                                                                                                                       |   採否   |
| :------------------------------------------------------------------ | :---------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------- | :------: |

### 4.2 確定運用手順（案 B の運用フロー）

1. **初期配置**:
   - `docs/c-ut/evidence/ut-bug-record.md` を作成し、Step 2 の全個別作業タスク（#140〜#148）ごとの記録用セクションおよび空テーブルをあらかじめ配置します。
2. **AI 作業工程での記録**:
   - TDD、テスト・型チェック等の自動検証、AIレビューのいずれであっても、確認済み不備を特定した時点で、検出 Issue のセクションに検出工程・手段と成果物区分を記録します。発生元 Issue が異なる場合は、由来欄に記載します。
3. **是正と証跡の追記**:
   - 不備の是正後、再現テスト、レビューコメント、修正コミット等を根拠として記録します。後続工程で同一不備を再度検出した場合は、新規計上せず既存記録に証跡を追記します。
4. **PR 本文へのサマリー記載**:
   - 各タスクの PR を作成する際、PR 本文の「検証」セクションに、確認済み不備の総数と成果物区分別・検出工程別内訳を記載します。製品コードのバグ密度に使う件数は支援成果物と分けます。例:
     ```markdown
     - C・UT確認済み不備: N 件（製品コード: P 件、支援成果物: S 件）
     - 製品コード不備（バグ密度の分子）: P 件
     - 検出工程内訳: Red 1 件、Green 1 件、AIレビュー 1 件
     - 詳細は docs/c-ut/evidence/ut-bug-record.md 参照
     ```

## 5. バグ密度メトリクスの算定方針

工程完了時に以下の 3 つの視点からメトリクスを算出します。

### 5.1 プロダクションコード規模ベース（件 / KLoC）

$$\text{バグ密度 (KLoC)} = \frac{\text{C・UT で確認した製品コード不備件数}}{\text{C・UT で追加されたプロダクションコード実ステップ数 (LoC)} / 1000}$$

- **対象コード**: `src/` 配下のプロダクションコード（テストコード `*.test.ts*`、Storybook `*.stories.tsx`、モック `src/mocks/**` を除外した物理行）。分子も `製品コード` 区分のみとし、テスト・モック等支援成果物の不備は含めません。
- **計測基準**: C・UT 開始コミットから HEAD までの「新規追加行数（insertions）」（※リファクタ等での行削除・短縮を相殺せず、C・UT で新規実装されたコード規模そのものを分母として評価するため）。
- **計測コマンド例**:
  ```bash
  # C・UT 開始時点のコミット（fb980ad）から HEAD までのプロダクションコード追加行数を取得
  git diff --shortstat fb980ad..HEAD -- 'src/**/*.ts' 'src/**/*.tsx' ':!src/**/*.test.*' ':!src/**/*.stories.*' ':!src/mocks/**'
  # 出力例: 15 files changed, 1250 insertions(+), 80 deletions(-) → 1,250 行 (1.25 KLoC) として算定
  ```

### 5.2 単体テスト規模ベース（件 / テストケース数）

$$\text{バグ密度 (Case)} = \frac{\text{C・UT で確認した製品コード不備件数}}{\text{C・UT で実装された単体テスト総ケース数}}$$

- **計測方法**: `npm run test:unit` の最終実行結果に出力される総テストケース数（例: `Tests: 120 passed, 120 total`）。この指標は規模で正規化した不備件数であり、テストケースの検出率ではありません。

### 5.3 原因分類別の比率・傾向分析

$$\text{原因分類比率 (\%)} = \frac{\text{各分類 (L / S / D / B / A) の件数}}{\text{記録バグ総件数}} \times 100$$

- 製品コード不備の原因分類比率を算出し、製品コードのバグ密度と対応させます。テスト・モック等支援成果物は、原因分類と検出工程を別集計し、製品コードと混在させません。

## 6. 工程承認時（No.11 #149）の集計・評価・標準化判定

### 6.1 集計手順

Step 2 の最終タスクである工程承認 Issue（[#149](https://github.com/high-soar/react-practice-notes/issues/149)）において、以下の手順で集計を行います。

1. `docs/c-ut/evidence/ut-bug-record.md` の全タスクセクションを集約し、確認済み不備の総数を成果物区分・検出工程・原因分類ごとに集計。
2. `npm run test:unit` を実行して単体テスト総ケース数を取得。
3. 製品コード不備件数のみを分子にして、プロダクションコードの純増行数（LoC）および UT ケース数で正規化したバグ密度を計算。支援成果物の不備は別集計。
4. `docs/c-ut/evidence/ut-bug-record.md` の「工程完了集計サマリー」テーブルに結果を記録。

### 6.2 振り返り観点と標準化判定基準

集計結果を踏まえ、人間レビュアーとともに以下の 3 観点で振り返りを実施します。

1. **開発リズム（オーバーヘッド）の評価**:
   - 記録作業が TDD のスピードや集中力を阻害しなかったか。
   - 記録フォーマットや項目に過不足がなかったか。
2. **品質メトリクスとしての有用性**:
   - 得られた製品コードのバグ密度や原因分類比率が、設計書の品質や実装の難所を客観的に示す指標として有効であったか。支援成果物の不備や検出工程別件数が、改善箇所の把握に役立ったか。
   - 後続の IT（結合テスト）工程での重点検証箇所の特定に役立ったか。
3. **計測上の限界**:
   - 本指標は AI 作業中に確認された不備の記録であり、未発見の不備を含む総欠陥数や AI が作り込んだ不備の数を示すものではありません。検出工程やレビュー実施状況の違いも踏まえて評価します。
4. **リポジトリ標準規約（`c-ut-workflow` 等）への正式採用判定**:
   - Step 3 以降や他プロジェクトにおいて、本運用を標準フローとして継続・昇格させるか、あるいは簡略化・見直しを行うかを判断する。
